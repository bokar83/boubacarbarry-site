TL;DR

Your five layout rules are now enforced by the publishing tool, not by an agent remembering them. Two of the five are injected automatically on every publish, so they cannot be forgotten. The other three are checked, and a page that fails them is refused before anything is copied, committed or pushed.

Collapse this block. It will stay collapsed on this page every time you come back, which is the actual point of the whole change.

72 of the 73 pages currently live under /review/ fail the new standard. Nothing was retrofitted. That is your call, and there is a recommendation for it below.

The five rules

"Hard rule: I like the TL;DR at the very top with the sections underneath. I always need to be able to collapse the TL;DR and the sections underneath the sections with toggles. I need to have a back-to-top button on every page. I need to have a navigation hamburger on mobile and regular navigation on the other that is floating if possible but that's not a requirement."

#RuleHow it is enforced now
1TL;DR at the very top, sections underneathChecked. Publish blocked if a section heading appears above it.
2The TL;DR is itself collapsibleChecked. Publish blocked.
3Every section collapsible with its own toggleChecked, per heading. Publish blocked, and it names the sections that are missing one.
4Back-to-top button on every pageInjected automatically. Cannot be forgotten.
5Hamburger on mobile, normal nav on desktop, floatingChecked. Publish blocked. The template ships a sticky nav, which is the practical version of floating.

Rule 2 is the one that kept getting missed. Pages gave every section a toggle and left the summary at the top permanently expanded, which is exactly the problem you described.

Default state, and why it is what it is

"I don't want to have to read 30 pages of a TL;DR to get to the content every single time. I need to be able to just quickly jump into this after future reviews."

The words that decided the design are every single time. That is a memory problem, not a default-state problem. So:

  • First visit: TL;DR open, every section open. The page reads top to bottom and hides nothing from someone opening it cold. A page that arrived fully collapsed would trade your first-read problem for a worse one.
  • Every visit after: exactly the state you left it in. Collapse the TL;DR once and it stays collapsed on that page. Fold away three sections you have already actioned and they stay folded.
  • One-tap reset: a floating Collapse all / Expand all button, bottom right, next to back-to-top.

The fold state is stored in your browser, per page. It is view state, never decision data, so it does not collide with the rule that decision pages need a real database. Losing it costs one tap, nothing else. Anything you actually decide on a page still goes to the database as before.

What actually enforces it

Four files in the site repo. The split is deliberate: inject what can be added safely to any page, check what cannot.

FileWhat it does
scripts/templates/review-page-template.htmlThe scaffold. Compliant out of the box. Every new page starts here.
scripts/inject-review-furniture.ps1Adds the back-to-top button, the fold-state memory and the expand/collapse-all control to any page, on every publish. Same idea as the version stamp: part of the flow, not a thing to remember.
scripts/validate-review-page.ps1The gate. Checks the collapsible TL;DR, the per-section toggles and the nav plus hamburger. One source of truth for what compliant means.
scripts/audit-review-pages.ps1Scores every page already live. Read-only, changes nothing.

Non-compliance now fails, it does not warn

A failing page is refused before anything is copied into review/, before the manifest is touched, before any commit. The page is built in a staging file first, so a rejected publish leaves no half-published folder behind.

There is one escape hatch, -AllowNonCompliant, which downgrades the gate to a loud warning and prints every broken rule. It exists so an urgent page is never blocked outright. It has to be typed on purpose.

A warning would have been useless here. A written rule that agents were trusted to follow is precisely what already existed, and it is why you had to ask a fourth time.

Also fixed

The version stamp was pinned to the top-right corner and sat on top of the sticky nav at phone width, which happened on two different pages the same day. Under 560px it now moves to the bottom-left corner, the one corner nothing else claims. Desktop is unchanged.

Recommendation on retrofitting

Do not retrofit all 72. Retrofit on touch: any page that gets republished for any reason now has to pass the gate, so the ones you actually use will fix themselves within weeks, and the dead ones stay dead at zero cost. If you want a batch anyway, the shortlist is the ten or so pages you still open, not the archive.

Run .\scripts\audit-review-pages.ps1 any time for the current count.

Why the existing rule failed, honestly

The rule already existed. It was written 2026-07-08, restated 07-28, sharpened 08-05, and restated again today. Pages still shipped broken every time. Three separate reasons, all confirmed rather than guessed:

  1. It stopped loading into sessions. The memory file carrying the rule was flipped to archive-tier this morning by the routine memory-index trim, along with 84 other entries, because the always-load index was over its size cap. A hard rule that does not load is not a rule. It is back to always-load now.
  2. The index it lived in was over cap anyway, so entries past the cutoff were being silently dropped even before the demotion.
  3. Nothing ever checked. The version stamp was the only piece of page furniture with any mechanical enforcement, and it is also the only piece that was consistently present. That is not a coincidence, and it is the whole argument for this change.

Reasons 1 and 2 will recur. Reason 3 will not, and reason 3 was doing most of the damage.
