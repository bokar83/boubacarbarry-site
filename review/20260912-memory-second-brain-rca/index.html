5. Recommendation: file-based-enhance vs DB-backed-replace

ENHANCE the file-based system. Do not replace it. One answer.

Reasoning, in the order that decided it:

  1. The DB-backed retrieval layer already exists. Postgres memory table, 5,800+ rows across 11 sources, tsvector plus vector legs, edge graph, a working query wrapper, nightly Notion sync. "Replace with a DB-backed service every agent queries at session start" describes the thing we have, minus the four missing roots and a schedule. Building it again is the Kitchen Sink.
  2. The files are the write path every agent already uses correctly. The Sahara lane filed a PRD, a ledger entry, a testing doc and a PRD-index row without being told. A replacement store would need every writer re-trained; the enhancement needs zero writer changes.
  3. A second store that can drift is the failure the system already survived once. atlas-memory records the SYS-14 consolidation principle for exactly this reason, and docs/ROUTING.md bans a new top-level store outright ("a tenth store is the disease").
  4. Gate cost. Enhance = 5 small edits under gate in one branch, one tap. Replace = weeks of orchestrator/ work behind the same gate, during a revenue-first window that bans new builds not tied to revenue.
  5. What "replace" would actually buy is semantic recall and Notion/Drive reach. The vector leg is already live; Notion reach is an extension of a running cron; Drive is out of scope until someone names a Drive fact an agent asked him for (none in this incident).

What "enhance" must include to be honest: the four roots, the schedule, the corrected freshness signal, the Notion DB extension, and the pre-ask reflex. Without the reflex (F2), a wider corpus is a better-stocked shelf nobody walks to.

6. Recommendation: workaround vs structural fix for the SessionStart/subagent gap

STRUCTURAL fix, sequenced in two steps. One answer.

The gap is real (two confirmations today) and it is architectural: Claude Code fires SessionStart for the main session and SubagentStart for spawns, and only the latter's additionalContext lands in a subagent. No prompt discipline closes that. The spawner-prompt workaround has already been tried for the copy battery, the TL;DR rule and the [WIP] rule, and each one ended up as a hook precisely because the workaround failed.

Step A (Phase 2a, same gate branch): the pre-ask gate rides copy-battery-inject.js. ~500 bytes, folded as the 10th block in the hook that already reaches every subagent. This closes THIS complaint for subagents immediately after his tap, at a cost of roughly 150 tokens per dispatch.

CORRECTED post-pressure-test: item 17 (dispatcher-side pull-based retrieval) is the PRIMARY Phase 2b mechanism; item 16 (the push-based SUBAGENT_BOOT.md render target) is DEMOTED to an optional fallback. Subagents today receive ZERO bytes of the 75KB overflow (not "the same 75KB" as any prior baseline implied) -- so an 8KB SUBAGENT_BOOT.md pushed unconditionally to every dispatch would be NET NEW push, roughly +8KB x ~401 dispatches/week = ~800K tokens/week of new unconditional context. That is the opposite of Boubacar's own explicit constraint that this whole effort must REDUCE token/context usage over time via on-demand pull, never increase it via more push. Item 16 must never ship as an unconditional per-dispatch push without a specific stated byte budget that nets negative against current subagent context (which is currently zero, not 75KB), and only if item 17's measured effect (the weekly count from item 18) proves insufficient after it has run.

Step B (Phase 2b, its own PRD), PRIMARY mechanism -- item 17, a dispatcher-side PreToolUse hook on the Agent tool that runs the second-brain query against the dispatch prompt and prepends only the top-3 relevant hits. This is genuinely pull-based/on-demand: nothing is pushed unless the dispatch prompt's own content justifies it, and it is the only path that reaches Explore/Plan agents, which receive no CLAUDE.md or memory index by design.

Item 16, DEMOTED to an optional fallback only. A third render target in build_memory_index.py: frontmatter reach: subagent on a memory file routes its index_line into memory/SUBAGENT_BOOT.md, rendered under its own byte budget, delivered by a sibling SubagentStart hook. Same mechanism SYS-660 built, pointed at a second event. Curated by memory-curator under the same single-writer rule. Build this ONLY if item 18's weekly count shows item 17 alone is not moving the number, and only with a byte budget stated and justified against the zero-byte baseline, never assumed.

Why not ship the whole overflow to subagents now (independent of the 16/17 ordering above): 75,374 bytes is roughly 19k tokens, and CLAUDE.md's own measurement is 401 dispatches per week. That is ~7.5M tokens a week to deliver rules of which perhaps twenty apply to any given subagent. The structural answer is a budgeted subset, and choosing the subset is a curation job that has not been done.

Named limits of the recommendation: Explore and Plan agents receive no CLAUDE.md or memory at all by design (that is the 61% token saving), so the pre-ask gate reaches them only through the dispatcher-side auto-retrieval in Phase 2b. Non-Claude-Code runtimes are SYS-700's problem and stay there.

10. Council review result (skill invoked, five voices + cross-review + synthesis)

THE CONTRARIAN. The fatal flaw: the plan's core mechanism is a text rule, and this exact rule has already been written in five places and ignored in all of them. Adding a sixth surface is the move that already failed. Second flaw: the ordering trap. If the pre-ask rule lands before the corpus widens (and the corpus widen is gate-held), the first thing every agent sees is ask.sh returning nothing for the Sahara question, and the rule dies in a week (SYS-531 section 2b said this in August). Third: ask.sh is an SSH round-trip; a subagent with no VPS access will silently skip it.

THE FIRST PRINCIPLES THINKER. The question as asked is "how do agents find things". The actual problem is that asking Boubacar is free for an agent and searching is expensive, so the cheap path wins every time. Reframe: make the ask itself malformed without a search receipt. A question to him without a Searched: line is an incomplete deliverable, the same way a decision without a reason is a fossil in ROUTING.md. That converts a soft instruction into a checkable shape, which a Stop hook can see. The corpus widen is necessary but it is not the lever; the receipt is.

THE EXPANSIONIST. The plan under-sells continuity-v2. It indexes what actually happened in every session, which is the only store that does not depend on anyone filing anything. The 10x play is not "remind the agent to search" but "search for the agent": the dispatcher already runs a PreToolUse hook on Agent (explore-routing-inject.js); a sibling that prepends the top-3 hits for the dispatch prompt makes every subagent start with the answer in hand. It also reaches Explore/Plan, which nothing else does. And the reach: frontmatter idea generalises to reach: codex, which is SYS-700's Phase 2.

THE OUTSIDER. From outside: 5,800 rows, 268 hard rules, a 24 KB cap, two settings files, 18 PreToolUse hooks, and nobody can say whether the problem is getting better or worse because there is no number. The obvious thing a customer would ask: how many times a week does an agent ask the human something the system already knew? Nobody measures it. Until that number exists, every fix is a feeling.
