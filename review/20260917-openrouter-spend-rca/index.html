2. The culprits, ranked

Ranked by how much spend each one explains, with the evidence attached. Where I can only bound a number rather than measure it, I say which.

#1 — The accounting itself, by design. Explains the whole 96.8%.

Not a bug. A comment in our own code, orchestrator/usage_logger.py line 418:

"CrewAI's LLM.set_callbacks overwrites litellm.callbacks on every Crew init, so this won't catch CrewAI calls — that's by design (CrewAI calls aren't logged in Phase 1)."

Phase 2 was never built. Every crew — absorb, studio, griot, newsletter, content-connection, the night crews — runs through CrewAI, and none of it has ever appeared in the ledger. On top of that, an audit of every call site in the repo found 19 more places that build their own HTTP client and never touch the logger, including the public website-audit tools and the live voice pipeline.

The worst of them: orchestrator/llm_router.py. Two different callers describe it in their own docstrings as "the logged chokepoint". It logged nothing. It enforced the spending caps and kept no record — so it could tell you a limit was hit and never who hit it. fixed on this branch

#2 — The overnight cron window. $46.54 of $91.76 over 11 days.

Measured above. 100 scheduled jobs, 51% of spend in six unwatched hours, peaking at 07:00 MT. The single clearest example of what lives in there:

ai-visibility-weekly fires every Sunday, makes 180 API calls across three engines, and has returned 0.0%–0.0% answered on every engine on every run since it was first installed. It writes an HTML report nobody opens. That is not a cost problem to optimise, it is a job to switch off.

#3 — The lead-magnet miner, paying for output it throws away. $2.50–$5.50 every Monday.

This one I reproduced end to end. scripts/lead_magnet_miner.py loops over every candidate file and makes one Claude Sonnet 5 call per file, direct, invisible to the ledger. Real counts from its own log:

RunFiles collectedReal API callsWindow
Mon 31 Aug91327413:30–13:50 UTC

Roughly 40–60% of them end in this line:

WARNING extract LLM failed for <file> ('NoneType' object has no attribute 'strip'); using heuristic

The cause, verified against the live API today, not guessed: extended thinking is on by default on Sonnet 5. Those reasoning tokens bill as output, and they come out of the same 400-token ceiling the script set. On a real 6,000-character file the thinking eats the budget, the answer never gets written, the call is billed anyway, and the code falls back to a keyword heuristic. I ran the identical payload twice: with the default, thinking present and the answer can come back empty; with thinking switched off, 49 completion tokens, zero reasoning tokens, clean answer, $0.0006. fixed on this branch

The dollar figure is a token-based estimate, not a measurement — I can count the calls exactly but not price them individually, for the reason in section 6. It explains perhaps a third of the Monday anomaly. The rest of the Monday cluster is still unidentified.

3. Yes, the meter itself is broken — three separate ways

You asked whether we are measuring this properly. We are not, and it matters for reading every number above.

  1. The system's own "spend today" figure is about a seventh of reality. The nightly snapshot reads OpenRouter's usage_daily, which resets at UTC midnight — 18:00 your time. The snapshot runs at 23:55 MT, so it captures the 18:00–23:55 slice and calls it the day. That is why provider_billing shows ~$1/day while the truth is ~$7.23. This exact bug was found and fixed on 10 May 2026 — in the dashboard only. The snapshot and the guard never got the fix.
  2. The guard is blind during your evening. Same cause: its cumulative alarm compares a counter that just reset to zero at 18:00 MT, so from 18:00 to midnight it structurally cannot see a spike.
  3. The "who spent it" block in every alert is empty by construction. It computes unattributed = today's total minus what the crews report. Since the crews report 3%, it has always said "unattributed", every time. The alert has been telling you it does not know, for months.

One correction in the other direction, and you should hear it from me first. The $8.34/day baseline is measured over a period that contains roughly 16 hours of freeze, during which autonomous work was switched off. So the true unfrozen burn is higher than the number on this page. When the freezing stops, spend will go up before anything brings it down. That is the fix working, not failing.

Built, tested, thrown away The per-job spend bracket

My main idea was to bracket every scheduled job with a reading of OpenRouter's usage counter before and after, and record the difference against the job name — attribution for all 69 wrapped jobs without touching a single call site. I built it and tested it on the live box. It wrote rows. Then I ran the control:

Test jobWhat it actually costWhat the bracket recorded
one real Sonnet 5 call$0.003334$0.004434
/bin/echo hello — zero LLM calls$0.00$0.033805

OpenRouter's counter lags a call by about 60 seconds and lands in stages, so the bracket has to hold a two-minute window — and on a live box that window swallows whatever else the system is doing. It would have put real dollars against jobs that spent nothing, in the one table whose whole value is that its numbers are true. I removed it. The tempting option was to ship it with a caveat in a code comment; nobody ranking jobs by cost six weeks from now reads the comment.

It stays in git history so the next person with the same idea finds the measurement that rules it out. The test rows were deleted and I read the count back at zero.

7. The one question only you can answer

What is the monthly OpenRouter number you are actually willing to pay for a system that is not yet producing revenue?

Every other decision here is downstream of it.

  • At $250/month — roughly where you are — the answer is a kill list and tighter jobs.
  • At $500/month the answer is to leave it running and spend the effort on instrumentation instead.
  • At $100/month the answer is that most of those hundred scheduled jobs stop this week.

Nobody can set that number but you. Without it, the guard's baseline gets tuned against a measurement rather than an intention — which is exactly how it ended up sitting at $2.00 while reality ran at $8.34.
