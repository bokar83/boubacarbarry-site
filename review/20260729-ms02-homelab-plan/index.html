Day-One MS-02 Setup

Order matters: identity and encryption before anything touches the network; the box is at its most exposed in the first hour, unpatched and un-encrypted, so close that window first.

  1. Unbox, connect wired Ethernet (never rely on Wi-Fi for a 24/7 host), power on, complete Windows 11 setup with a local admin account (Microsoft account optional — a local admin plus Windows Hello PIN is enough for a single-operator home box).
    Click-by-click: local admin account during Windows 11 setup (OOBE)
    1. Power on. On the network screen, connect the wired Ethernet cable — Windows should auto-detect it; if it insists on Wi-Fi setup, look for a small "I don't have internet" / "Continue with limited setup" link to skip past the Microsoft-account push.
    2. If Windows still pushes a Microsoft account sign-in screen, look for "Sign-in options" (small text link, easy to miss) → "Offline account" / "Limited experience" → confirm past the "are you sure?" warning screen.
    3. Enter a username for the local account when prompted (this becomes the Windows username — note it, since Section 5 step 4's memory-junction discovery depends on knowing it).
    4. Set a password for the local account (or leave blank + confirm if prompted — a password is recommended since this account also gets Windows Hello PIN layered on top in step 5 below).
    5. Answer the privacy/telemetry screens (location, diagnostics, ads) per personal preference — none of these affect anything else in this plan.
    6. Let Windows finish "This might take several minutes" and land on the desktop.
  2. Confirm Windows edition is Pro (required for BitLocker and for WSL2/Hyper-V platform features to be fully available — MS-02 units typically ship Pro, but verify via winver before proceeding; if Home, upgrade to Pro first).
  3. Run Windows Update to full patch level, reboot as needed, before installing anything else.
  4. Enable BitLocker full-disk encryption (TPM + PIN) on the system drive. Do this before any data of value lands on the disk — enabling it later re-encrypts in place but there's no reason to wait.
    Click-by-click: enable BitLocker (TPM + PIN)
    1. Set the Group Policy prerequisite FIRST — skip this and the PIN prompt in step 8 below silently never appears. Confirmed live: Windows 11's BitLocker wizard only offers "Enter a PIN" as an authentication method if this policy is configured; without it, the wizard proceeds straight to TPM-only encryption with zero indication anything was skipped. Press Win+R, type gpedit.msc, Enter → Computer Configuration → Administrative Templates → Windows Components → BitLocker Drive Encryption → Operating System Drives → double-click "Require additional authentication at startup" → set to Enabled → under "Configure TPM startup PIN" (in the options below the radio button), set the dropdown to "Require startup PIN with TPM" → OK. If gpedit.msc says "Windows cannot find gpedit.msc" — that means this is Windows Home, which has no Group Policy Editor; see the Windows Home box at the bottom of this toggle before continuing, and do not guess a fix without it.
    2. Confirm TPM is present and ready. Press Win+R, type tpm.msc, Enter — the "Status" panel should say "The TPM is ready for use." (Alternatively, PowerShell: Get-Tpm and check TpmReady : True.) If it isn't ready, it needs enabling in BIOS first — see the BIOS toggle below (item 6); most modern boards ship with it on by default.
    3. Open Control Panel (search "Control Panel" from Start) → System and Security → BitLocker Drive Encryption. (The newer Settings → Privacy & Security → Device encryption path also exists in Windows 11, but the classic Control Panel path gives the TPM+PIN option this plan wants — Device encryption alone is TPM-only, no PIN.)
    4. Next to the C: drive, click "Turn on BitLocker."
    5. Back up the recovery key BEFORE encryption starts — do this deliberately, don't accept the first option by reflex. You'll be offered: save to your Microsoft account, save to a USB flash drive, save to a file, or print it. Pick a location you will actually be able to reach during a real recovery (a password manager entry or a printed copy filed somewhere durable beats "whatever the wizard defaulted to") — note in this plan's own notes section (bottom of this page) where you put it.
    6. Choose "Encrypt entire drive" (safer for a drive that's had any prior data on it) vs "Encrypt used disk space only" (faster, fine for a truly fresh drive) — for a fresh MS-02 setup, used-space-only is fine.
    7. Choose the "new encryption mode" (the more compatible XTS-AES setting is the default and correct choice) → Continue.
    8. When prompted for authentication method, choose "Enter a PIN" (this is the TPM+PIN mode this plan specifies, not TPM-only) → set a 4-20 digit PIN → confirm it. If this "Enter a PIN" choice doesn't appear and Windows goes straight into encrypting, step 1's Group Policy setting wasn't applied — stop, don't restart, and use the recovery box below to add the PIN after the fact instead of starting over.
    9. Click "Start encrypting" — it runs in the background; you can keep using the PC. Confirm completion later via the same BitLocker Drive Encryption panel (should show "BitLocker on").

    Already encrypted without the PIN prompt? Add the PIN now — no restart, no undo needed

    This is the exact situation that happened live on this walkthrough, and this exact fix confirmed working: (1) apply the Group Policy step above (gpedit.msc → same path → "Require additional authentication at startup" → Enabled → "Configure TPM startup PIN" → "Require startup PIN with TPM"). (2) Open an elevated PowerShell or Command Prompt (right-click Start → "Terminal (Admin)") and run:

    manage-bde -protectors -add C: -TPMAndPIN <pin>

    Replace <pin> with a 4-20 digit PIN. This adds the PIN protector alongside the existing TPM-only protector on the drive that's already encrypting or already encrypted — it does not restart the encryption, does not require decrypting first, and does not touch data. Confirm it took by running manage-bde -protectors -get C: and checking for a "TPM And PIN" or "Numerical Password" protector alongside "TPM." Reboot once afterward to confirm the PIN prompt actually appears at startup.

    If gpedit.msc doesn't exist (Windows Home): the Group Policy Editor isn't available, but the same setting can be written directly to the registry it would otherwise configure — researched and cross-checked against two independent documented BitLocker registry references (not verified live on a Home machine in this walkthrough, unlike the gpedit.msc path above, which was). In an elevated Command Prompt:

    reg add "HKLM\SOFTWARE\Policies\Microsoft\FVE" /v UseAdvancedStartup /t REG_DWORD /d 1 /f
reg add "HKLM\SOFTWARE\Policies\Microsoft\FVE" /v UseTPMPIN /t REG_DWORD /d 1 /f

    Then run gpupdate /force (or just restart) before the manage-bde -protectors -add command above. If this still doesn't produce the PIN prompt or protector, stop guessing further registry changes — flag it to research/support rather than trial-and-error on a security setting.

  5. Set Windows Hello PIN / biometric for local login.
    Click-by-click: set up Windows Hello PIN
    1. Open Settings (Win+I) → Accounts → Sign-in options.
    2. Under "Ways to sign in," find "PIN (Windows Hello)" → click "Set up" (or "Add").
    3. Verify the local account password when prompted.
    4. Enter a new PIN, confirm it. There's a checkbox for "Include letters and symbols" — optional, leave off for a plain numeric PIN unless a stronger PIN is wanted.
    5. Click OK. The PIN is active immediately — no restart needed, but signing out and back in is a good way to confirm it works before relying on it.
  6. In BIOS/UEFI: set "restore last power state" or "always on" for after-power-loss recovery (see Section 8's 24/7 operation notes), confirm wired NIC is set to a fixed/reserved DHCP lease at the router, and disable any factory bloat auto-launch.
    Click-by-click: BIOS AC-power-recovery setting + the DHCP-lease correction + disabling bloat

    Confirmed live from the real MS-02 Ultra BIOS — screenshot-verified, not a guess

    2. Navigate to Advanced > ACPI Settings (confirmed live — this is where the AC-power-recovery field actually lives on this board, not under "APM Configuration" or "Power Management").
    3. Find the field named "AC Failure Resume" (confirmed exact field name from the live BIOS screen; on-screen description reads: "Specify what state to go to when power is re-applied after a power failure (G3 state).").     4.     2. Click "Rename this PC" (the About and Home pages both also show a quick "Rename" shortcut button near the top).
    3. Type the decided name: BAOBAB-10K-HQ (13 characters — within Windows' 15-character / valid-NetBIOS limit, letters/numbers/hyphens only, no leading/trailing space, so it's typed exactly as-is with no adjustment needed).

    5. After restart, confirm via PowerShell: ipconfig /all — check the wired Ethernet adapter section shows an active IPv4 address and the Wi-Fi adapter (if present) shows "Media disconnected" or no address, confirming it's really on the wired path.
  8. Install and configure the UPS's monitoring software (see Section 8) and confirm the MS-02 sees a "on battery" signal in a manual pull-the-plug test before trusting it unattended.

Software Installation Order

Why WSL2, not Hyper-V/VMware/VirtualBox/Proxmox (click to expand) — the hardest call in this plan

The hardest call in this plan: virtualization for Home Assistant + Zigbee USB + Docker on a Windows daily driver

Recommendation: WSL2 as the single virtualization layer. No Hyper-V-standalone VMs, no VMware, no VirtualBox, no Proxmox-as-host. Run Home Assistant as the "Home Assistant Container" image inside Docker (WSL2 backend), and pass the Zigbee USB coordinator through with usbipd-win.

Why, considering all four constraints at once (HAOS + Zigbee USB passthrough + Docker + Windows-desktop-daily-driver):

  • USB passthrough is the deciding factor, and it rules out full HAOS-as-VM. The "proper" Home Assistant OS ships as a VM image expecting real USB passthrough. Hyper-V's only passthrough mechanism (Discrete Device Assignment) is unreliable for USB, RemoteFX is deprecated, and consumer Hyper-V support for it is thin. VMware Workstation and VirtualBox both do proper USB passthrough well — but both fight Hyper-V for the CPU's virtualization extensions, and WSL2/Docker Desktop already require Hyper-V's platform underneath. Running a second hypervisor engine "alongside" Hyper-V means one of them runs degraded through the Windows Hypervisor Platform (WHP) shim, and that's exactly the class of intermittent, hard-to-diagnose conflict a homelab veteran will have hit before (VM hangs on resume, USB devices silently drop, WSL2 networking breaks after the other hypervisor starts).
  • The fix is to stop needing a VM's USB passthrough at all. Microsoft's own usbipd-win project attaches a USB device (the Zigbee coordinator) directly into a WSL2 distro over USB/IP — it's maintained, well-documented specifically for Zigbee/Z-Wave dongles, and doesn't touch Hyper-V's device model at all. Inside that WSL2 distro, run Docker Engine natively via systemd (not Docker Desktop — see the callout below for why) and run Home Assistant Container (the plain container image) instead of full HAOS. You lose the Supervisor's one-click add-on store; you gain the ability to run every add-on's equivalent (Zigbee2MQTT, Mosquitto, ESPHome, etc.) as its own ordinary Docker container in a docker-compose.yml — which is more reproducible, source-controllable, and consistent with how agentsHQ itself is already run.
  • This also directly serves agentsHQ. WSL2 + Docker (Engine, running natively inside WSL2 — not Docker Desktop) is the same stack agentsHQ's own local dev already assumes (Docker Compose, volume-mounted code). One virtualization layer serves both the home-services stack and the agentsHQ local tooling — not two separate systems to keep healthy.
  • Rejected: Proxmox (or ESXi) as the host OS, i.e. making Windows itself a guest. This is the biggest-blast-radius option on the table: it adds a full bare-metal hypervisor layer under a machine whose primary job is being Boubacar's daily-driver desktop, complicates GPU access for both daily use and Plex hardware transcode, and trades away simplicity for a flexibility this one-person, single-box, 6-month-to-NAS setup doesn't need. It would make sense if this box's job were "run several server VMs" — it isn't; its job is "be a desktop that also runs a few background services."
  • Rejected: Hyper-V-standalone VMs for the same USB-passthrough reason above, and because it forecloses ever using VMware/VirtualBox later without a fight.
Why NOT plain Docker Desktop autostart (click to expand) — real gap found, corrected to WSL2-native systemd

Real gap found researching the click-by-click steps: Docker Desktop's own autostart is NOT true headless autostart

Section 10 (validation checklist, item s10-5) and Section 8 both assume "Docker Desktop starts on boot without interactive login" is achievable via a simple setting. It isn't — Docker Desktop's "Start Docker Desktop when you sign in" option still requires an actual interactive Windows sign-in to have happened first; it is not a background-service autostart. For a box meant to come back up fully unattended after a power loss (this plan's own Section 8 requirement), there are two real options, not one simple toggle:

  • (a) Enable Windows auto-login for one dedicated local account, so Windows reaches a signed-in desktop on its own and Docker Desktop's sign-in-triggered autostart then fires. Real tradeoff: auto-login weakens the "BitLocker + PIN" security posture this plan builds Day 1 — anyone with physical access reaches a logged-in desktop without the PIN. Worth Boubacar's explicit decision, not a silent default.
  • (b) Skip Docker Desktop for the always-on stack and run Docker Engine directly inside the WSL2 Ubuntu distro via systemd instead. Add systemd=true under [boot] in /etc/wsl.conf, run wsl --shutdown from PowerShell to apply it, then inside that WSL2 shell run sudo systemctl enable --now docker.service. This starts with WSL2 itself — no Windows interactive login needed at all, and no auto-login tradeoff. This is the better fit for this plan's own 24/7-unattended requirement, and is the recommended fix — flagged here as a real correction to Section 4/8's original assumption, not just a click-by-click gap.

Decided (v11): (b). It solves the actual requirement (unattended restart) without weakening Day 1's BitLocker+PIN security decision, and Docker Desktop's GUI was never needed day-to-day — docker compose commands work the same against the WSL2-native engine, run from inside the WSL2 shell.   2. Run wsl --install. This single command enables the Windows features WSL2 needs (Virtual Machine Platform + Windows Subsystem for Linux), downloads the WSL2 Linux kernel, and installs Ubuntu as the default distro — no separate steps needed on a current Windows 11 build.
