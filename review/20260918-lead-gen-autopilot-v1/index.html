Lead-Gen Autopilot v1 — build review

Signal Works reply autopilot · 2026-09-18 · four phases, one branch, verified against a frozen 36-line acceptance contract

TL;DR

Built and verified. One contract line cannot pass, and it is not this build that broke it.

  • The reply autopilot works: it watches Signal Works reply threads, sorts each reply into six buckets, drafts a response into Gmail Drafts, and attaches a Calendly link only when someone is genuinely interested.
  • It cannot send anything. Proven five separate ways, not asserted. Nothing in the new code can reach a send function, and a live test fails the instant any transport is touched.
  • Independent QA executed all 36 lines verbatim: 33 of the 34 blocking lines PASS, including all three non-negotiable no-send lines, which QA read in full and judged genuine rather than surface-level. The 34th asks the whole repo test suite to exit clean, and that suite has 127 failures that exist without this build.
  • A review pass after QA found a real defect and it is now fixed. On the live path every reply would have been read as an empty message, and the live mode was what ran by default. Both closed, re-checked, and a test now exists that would catch it coming back.
  • Released to merge, dormant. Nothing is scheduled and nothing runs on its own. Seven known limits are named below and all of them must close before it is ever put on a timer.

What it does, in plain terms

Today a person reads every reply to the Signal Works outreach emails and decides what to do next. This closes that gap without taking the decision away.

StepWhat happens
1. WatchPolls the sending mailbox for replies, only on threads the outreach pipeline itself started. Unrelated inbox mail is ignored.
2. SortSix buckets: interested, not interested, wrong person, unsubscribe, out of office, needs human judgment. Anything ambiguous or garbled goes to needs-human-judgment on purpose. It never guesses.
3. DraftWrites a reply into Gmail Drafts. Only the interested bucket gets a single-use Calendly link. Every other bucket gets a short draft or a logged no-action.
4. You decideYou read it in Gmail, edit it, send it yourself. The system has no way to send.

Gmail Drafts is the review surface by design. No new page was built, which is why there is nothing to click here beyond this report.

The no-send guarantee, and its honest limit

This was the part worth being paranoid about, so it is proven in layers rather than claimed once.

  • Compiled-code scan: no send-capable symbol name appears in any module.
  • Import scan: no mail-transport module is imported anywhere, including inside functions.
  • Raw text scan: catches a name assembled at runtime to dodge the first two.
  • Live namespace check: after actually importing every module, nothing send-capable is bound.
  • Live tripwire: a full dry pass over six sample replies with the network replaced by something that fails the test the moment it is touched.

The limit, stated rather than buried: a name split across fragments in the source would defeat the four static layers, and only the live tripwire would catch it. The test file says so itself. Two reviewers read that file independently and reached the same conclusion about what it does and does not prove.

The one line that does not pass, and why it is not this build

Contract line 3 asks the whole repository test suite to exit clean. It does not, and it did not before this build existed. Independent QA ran it verbatim and recorded FAIL.

python -m pytest tests/ -q
-> exit 1 :: 131 failed, 2699 passed, 38 skipped, 9 errors, 96m09s
  • Zero of those failures are in the new code. QA confirmed this by grepping its own full log, and separately by the fact that the changes are confined to two new directories nothing else references.
  • Three separate full runs happened across the build, at three different commits, each around 96-97 minutes: 128, then 127, then QA’s 131 failures. They sit on different trees and are not directly comparable to one another.
  • A dedicated piece of work has since measured the suite properly on its own branch: about 111-112 failures that fail every time, plus 5-6 genuinely unreliable tests concentrated in a single file, and the 9 credential errors removed by skipping them when the database is unreachable. Those figures come from a tree with fixes already applied, so they are not the same measurement as the three above.
  • The contract also expected a recorded before-build baseline to compare against. None was ever committed, so there is no clean subtraction to point at.

Recommendation: accept the build with line 3 recorded as failed for a pre-existing reason. Repairing the repository test suite is real work and it is already underway on its own branch. Holding this build behind it would mean holding it behind a problem it did not cause, and the strict reading of the contract is what produces the not-accepted verdict, not any defect in what was built.

What the review pass caught after QA passed it

QA signed off 33 of 34 lines. A separate adversarial read afterwards found something the contract never asked about, and it was serious.

  • Every real reply would have been read as blank. The part that fetches replies was handing on a different set of fields than the parts that read them, and it was never fetching the message body at all. A reply saying yes and a reply saying never contact me again would both have arrived as an empty message. Worse, an interested verdict on that emptiness would have burned a real calendar booking link into a draft addressed to nobody.
  • Live mode was the default. Running the module with no arguments would have gone straight at the real mailbox. It now takes a typed flag to go live, and doing nothing gets you the safe sample pass.
  • Why nothing caught it earlier: the safe sample pass supplied its own made-up replies, in the shape the rest of the code wanted. The fixtures and the real thing disagreed, and only the fixtures were ever tested. Every gate before this one was reading the same fiction.

Both are fixed. The field list now lives in exactly one place, so the two halves cannot drift apart again, and a new test derives both sides from that one definition — run against the old broken version it fails seven times, which is the proof it would catch a repeat. A second review then traced a real Gmail message all the way through and confirmed the classifier now receives the actual words and the draft goes to the actual person.

The honest read: this is what the review chain is for. Had this merged when the contract said it could, it would have sat there looking verified, and the danger was never that it sits idle — it is that someone puts it on a timer in three weeks believing it was checked.

Seven things that must close before it runs on a timer

None of these block the merge, because nothing is scheduled. All of them block scheduling. They are written into the code itself, not just here.

  1. It remembers nothing between runs, so a second run re-drafts every reply and burns fresh booking links for people already handled.
  2. A Gmail hiccup mid-run kills the whole pass, and with nothing remembered, everything done so far is lost.
  3. If the database is unreachable it reports no replies, which looks identical to a quiet day. A failure that looks like success.
  4. If the classifier service is down, every reply is filed as needs-a-human, and the run still prints clean.
  5. Unsubscribes are logged and nothing more. There is no suppression handoff behind it. Compliance-adjacent, so this one matters most.
  6. The guard meant to stop the blank-reply bug returning only blocks one exact spelling; a near-synonym slips past it.
  7. A safety check that catches a reply with no sender address was written but never wired in, so that narrow case can still draft to nobody.

Findings worth keeping
  • A real bug caught during the build. An over-eager fuzzy match was mapping garbled model output to interested — the exact wrong direction. Removed. Garbled input now lands in needs-human-judgment.
  • Tests were making live calls to a paid service. Found while investigating the slow suite: some tests fired real, billable requests whenever a key happened to be present, and only looked green on machines that had none. Fixed on a separate branch.
  • A measurement mistake worth remembering. Three of us concluded the test suite was hung. It was not. Each had set a timeout shorter than the 97-minute runtime. Agreement between people using the same flawed method is not confirmation.
  • Thinnest coverage named, not hidden. Of the four production files, the watcher has the least test coverage at 66 percent. Everything the contract asked for passes; this is simply where a future gap is most likely to appear first.
  • Contract defect for the next revision. Line 3 as written can never pass in this repository, for any build, because it assumes a clean baseline that has never existed. It should compare against a named, recorded baseline instead. That rewrite belongs to the spec author and was deliberately not done here.

What happens next

Nothing needs doing from you for it to land. It is released and dormant.

The one thing I would ask for: when you next have a day of real replies, let it draft against them by hand and read what it writes. Everything proven so far was proven against invented replies, and the defect above is exactly what that blind spot produces. The value of this thing is the quality of the drafts, and nobody has yet seen it face a real person writing back.

Do not put it on a timer yet. The seven items above are why, and the fifth one — unsubscribes being logged and nothing more — is the one I would close first.
