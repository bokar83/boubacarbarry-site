01One-Line Verdict

GO — but phased, and phase 0 is the money watch, not the Chief of Staff.

Founder-weight screen (three doors)

This is a door-1 build: it takes ongoing operational weight off your plate. Today you are the closure mechanism (an item only leaves the board when you hand-edit a database row) and you are the dispatcher (it surfaces, you act). v2 removes both jobs.

The door-3 risk is real and named: if the estimates are wrong or the verifications are noisy, you become the corrector of an agent instead of the operator of a board, which is a worse job than the one you have now. Section 13 makes "he corrects it less than 1 run in 5" a ship-blocking success signal precisely so that drift gets measured rather than assumed away.

04What We Will NOT Build

Twelve vetoes. Each is a thing a reasonable person would put in v1, with the reason it is out. A 21-section spec that scopes everything is a failed spec.

  1. No social engagement read-back. The publishing integration is write-only; a grep for any insights or analytics endpoint returns zero hits, and no read path exists anywhere in the repo. It will reason about social with a stated blind spot and never estimate a number. A guessed engagement figure is worse than a named hole.
  2. No competitor ad-spend intelligence. The adapter raises NotImplementedError and the platform's public ad library is political-ads-only. Not a credential gap, and no amount of money buys it.
  3. No freelance-marketplace board. It has a real database and it is reachable, but it is a hands-off lane. That is a policy constraint, not a technical one, and it is yours to lift (OQ-3). Default: out.
  4. No coaching-programme connector. No public API; state is re-swept by hand. It reads the existing rows and labels their age rather than pretending to a live feed.
  5. No new dashboard, decision page, or review surface. A new page is a second thing to remember to look at, which is the original failure.
  6. No new table. Everything it persists goes to display keys or to the two ledgers that already exist.
  7. No agent-authored 12-week year and no agent-invented targets. A commitment invented by an agent is worthless as a scoreboard. It may draft a number with its derivation; the number is yours.
  8. No autonomous send to any human, ever, in any version.
  9. No re-implementation of the Council or the review rubric. Both exist.
  10. No replacement of the morning brief or the on-demand line. v2 is a layer under them: it changes what they have to say, not what they are.
  11. No monitor. Nothing proactively watches between the scheduled pass and your next call — except the spend watch, which watches the system, not the world.
  12. No trust-ladder promotion machinery. v4 specified four gates before any decision class could go from advise to act. You replaced that with the damage list on 2026-08-07. The gates are not built; the damage list is the boundary. Deliberate simplification, residual risk named in section 12.

06The User Who Matters

You, 08:15 on a weekday, coffee, before the first meeting. You have roughly 90 minutes of your own attention to spend on revenue today, a session on Aug 19 with 0 of 20 seats sold, and another on Aug 27 with 0 of 30. Phase 1 — Closure as verification.

The recon's sharpest finding: a marker sweep would retire 22 dead rows and zero of the four items you complained about, because nobody had marked those four closed. Both halves are needed and they compose.

  • 1.1 The cheap half: the ranker learns to read CLOSED / DONE / SUPERSEDED / RETIRED and skip those rows, mirroring a done-check that already exists for a different row type. Retires 22 rows on day one for near-zero cost.
  • 1.2 The real half: a verification pass, run before ranking, on the survivors only. Each item carrying a checkable claim is checked against the system that actually knows. Cheap-first: never verify a row a human already closed.
  • 1.3 Three states, never two: VERIFIED-CLOSED / VERIFIED-OPEN / INCONCLUSIVE, each with a mandatory evidence string naming the source, the query and the timestamp. A state with no evidence string is a bug, not a state.
  • 1.4 A verified closure writes back through the single controlled writer, prefixing the row. The parser from 1.1 then retires it. The two halves compose: 1.2 supplies the truth, 1.1 supplies the retirement. Nothing deletes your prose.
  • 1.5 It also writes a row to the existing closure ledger, so the closure is queryable and reversible.

Fail-open or fail-closed — stated explicitly, because getting it wrong reproduces the original bug in the opposite direction

INCONCLUSIVE fails OPEN. The item stays. The cost is asymmetric and this system already knows it: the existing discharge code reasons in its own docstring that "a FALSE done silently removes a real obligation... and he would never know." A false close is invisible and unrecoverable. A false open costs you one line you can correct.

Fail-open is BOUNDED, or it becomes today's bug wearing a new hat. Two bounds, both required:

  1. An inconclusive item renders in its own bucket, never mixed into the ranked set. It can never win the number one slot on an unverified claim. Ranking on an unchecked number is exactly the failure phase 1 exists to remove.
  2. The same checker returning inconclusive for the same item on three consecutive days escalates as a checker-health defect — a Telegram naming the checker, not the item. The noise routes to the thing that is actually broken.

A verified closure is reversible in one line from you, and the ledger row is the audit trail. A verifier that throws is inconclusive, never closed. An exception is never evidence.

Proof

One real run in which the 22 marked rows leave the ranked set; each of the three live blocked-on-you rows resolves with a named evidence string, including at least one that correctly comes back inconclusive; and the hand-typed "0 registrations" is either confirmed against Stripe's count or the mismatch is stated out loud.

Phase 2 — The engine model and the two-axis ranker. No reasoning model yet.

Deliberately deterministic first. If the deterministic version already produces a sane grid, the Council's job in phase 3 is judgment rather than arithmetic — and if it does not, that is a finding worth having before adding $2.36 a day on top.

2.1 An engine registry. Eleven engines, each with a stable id, a brand, an owner lane, its mapped rows and its target state. Today the revenue ledger is bucketed by price tier, not by brand, so there is structurally no way to ask "how much has consulting earned versus the lead-generation product versus ghostwriting."

Untargeted must never mean invisible

All five dollar-denominated rows — the only money ledger on the board — are untargeted, 28 days stale, and therefore unrankable on the input that carries the most weight. Thirteen rows are in that bucket. The rule:

An engine with no target renders in a named UNTARGETED bucket, and exactly ONE action is generated for it: set the target. Addressed to you, one line, carrying a proposed number and the derivation of that number. You supply the number; it never does.

An unrankable engine becomes a one-decision item instead of a hole.

2.3 The two live products have no revenue bucket at all. The five price tiers were last touched 2026-07-10, before the Aug 19 and Aug 27 products existed. A real sale today would land as a registration count and would not roll into the "$3,000 by Sep 20" number at all. v1 adds per-engine revenue rows and lets Stripe populate them.

2.4 The two axes, both estimated — including for actions it generates itself

VALUE: expected dollars attributable to the action inside its own window, times confidence, bucketed HIGH / MED / LOW, anchored on the engine's target gap. It inherits the existing importance weights rather than replacing them; those are live and tuned and this build does not re-litigate them.

The load-bearing call

Effort is measured in YOUR minutes, not in work. An action that costs a dispatched agent three hours and you zero minutes is low effort. It dispatches; your attention is the scarce resource, not compute. A second field carries the machine cost separately and feeds the budget, never the grid.

Bands, not minutes, because a minute estimate invites false precision and gets argued with: S 30 min or less of your time · M up to 2h · L up to a day · XL multi-day.

Your marker wins. A row you have annotated with a time pins the band; the estimator does not override it. Human intent beats a model's guess, always.

Calibration, or the estimates are vibes. Every estimate is written to the prediction ledger already specced in v4, alongside the observed outcome when it lands. Reuse; do not build a second ledger. v4's own tripwire carries over verbatim: fewer than 20 resolved events in 14 days means the capture path is redesigned, not tuned.

2.5 The grid, with the fourth quadrant named the way you named it

Q1 · DO NOW · high value, low effort

Top of the list. Dispatched immediately if it is not on the damage list, surfaced to you if it is. This is where your 90 minutes go.

Q2 · DECOMPOSE · high value, high effort

Not queued as-is. Its job is to break the item into Q1-sized slices and rank those. A high-value item that stays XL forever is a planning failure, not a workload.

Q3 · BATCH · low value, low effort

Swept in one unattended pass by a dispatched agent. Never occupies your attention individually. Your words: "those are things we do last of all."

Q4 · KILL · low value, high effort

Killed, not queued. Written to a kill ledger with both estimates and the reason, removed from the board, reported once. Never silently. Reversible: one line from you relights it. Nothing is deleted.

Proof

One real run in which all eleven engines appear in exactly one quadrant or in the untargeted bucket — zero engines missing from output; the number one item carries a non-null effort band (today's carries none); a synthetic low-value high-effort item lands in the kill ledger and not the queue; and a row you annotated keeps your band.

Phase 3 — The Council pass. The expensive leg, and it only turns on behind phase 0.

Full multi-voice Council per engine — five voices, peer review, chairman synthesis — over that engine's evidence bundle and phase 2's candidate actions, plus one cross-engine ranking pass. This is the shipped default and there is no automatic fallback.

The step-down lever you asked for, yours to pull, never automatic: one environment variable with three settings — full (default), chairman-only (an existing single-call pattern already used elsewhere in production precisely because the full Council is "too heavy"), or off (phase 2's deterministic output). One variable, no code change.

A budget halt is not a step-down and must never look like one

If the per-run budget fires mid-pass, the run serves phase 2's deterministic ranking labelled as such and sends a Telegram. It degrades to a lower tier and says so. It never serves a partial Council result as if it were complete, and it never serves nothing.

Proof

One real pass producing eleven Council run ids; the joined cost measured and inside the per-run cap; and the honest one — the Council's output differs from phase 2's deterministic output in at least one named, defensible way. If it never does, the Council is decorative on this workload, and that is a finding worth $88 a month to learn, reported rather than buried.

Phase 4 — Dispatch.

It dispatches agents to execute what it identifies. It stops and asks only on the damage list: sends to real humans · public content in your name or a brand's · money · data destruction or migration · credentials, secrets, permissions · shared production infrastructure · weakening a hard rule · legal or compliance exposure. Everything else it just does.

  1. The screen fails CLOSED. An action it cannot confidently classify is HELD, not dispatched. Deliberately the opposite of phase 1: there, a false close causes invisible harm; here, a false dispatch causes real-world action.
  2. Dispatched agents inherit every hard rule — the copy gates, the no-send rule, the no-approval-marker rule, the branch tagging, worktree discipline, VPS read-only.
  3. Every dispatch and every hold is logged with the action, the screen result, the reason, and the artifact the agent returned. A dispatch with no durable artifact is incomplete.
Proof

One real revenue action dispatched end to end, returning a durable artifact the dispatcher independently verified; and one deliberately damage-list-tripping action (a drafted email to a real person) refused, held, and surfaced to you instead of sent.

12The Failure Modes — including nine things the recon could not verify

12.1 A false verified-closure silently removes a real obligation

The worst failure this build can produce, and worse than the bug it fixes, because it is invisible. Mitigations, all in phase 1: three states never two · inconclusive fails open · a mandatory evidence string · a thrown verifier is never a close · every closure is a stated note · one line relights anything · the ledger is the audit trail. Accepted residual: a checker that is confidently wrong closes an item wrongly. Not fully mitigable; bounded by the reversal path and by closures being reported rather than hidden.

12.2 Cost runaway

Mitigations: phase 0 ships first and gates everything · per-run hard cap · alerts at 60/80/90 · the cap-block tag gets a consumer · the budget is built on the worst observed Council run ($0.236), not the mean ($0.13) · the step-down lever is one variable. Accepted residual: the Council cost measurement is transferred, not native — the five observed runs are from 2026-04-21 reviewing consulting deliverables, with inputs ranging 10,642 to 90,153 tokens. Phase 3's proof measures it natively and the number gets corrected here.

12.3 It dispatches an action it should not have

Mitigations: the screen fails closed · every candidate is screened and logged, pass or hold · dispatched agents inherit every hard rule · no send, ever.

Accepted residual, named rather than buried

v4 specified a four-gate trust ladder before any decision class could be promoted from advise to act. This build replaces it with a category boundary (the damage list) rather than a competence boundary. The damage list answers "is this class of action dangerous?" It does not answer "is this agent good enough at this class yet?" That is a real gap. It is accepted because the damage list is decidable in seconds and the ladder is not built, and because you made the call on 2026-08-07. The mitigation is the dispatch log: if a pattern of bad non-damage-list dispatches appears, the ladder gets built and this gets re-opened.

Those two rooms are two-thirds of that goal, and both are empty with the windows closing. Its first job is to answer "what fills those seats" with a checked number and a ranked action rather than a report.

The second angle is time. You have roughly 90 minutes of revenue attention a day. Today a meaningful share of it goes to work the system should have done: reading a 134-item board, re-deciding what is already done, and dispatching by hand. The third is cost discipline. Phase 0 alone is worth shipping if nothing else ever ships, because a silent mid-day cap breach currently kills every autonomous crew until midnight with no notification at all.

20Voice & Tone Spec

For what it says to you

Lead with the answer. One sentence, then the why, then the evidence. No preamble, no "I have analysed." Never a header, table or bullet on line one. Bands and buckets, not false precision — "30 minutes or less of your time," never "27 minutes." Every fact carries its source: the render layer cannot emit a confident sentence without one, and a generated action is a sourced reading too.

Say "I do not know" plainly. Inconclusive is a real answer and gets stated as one, with the check that failed. Never "First move: NOT STATED" as a terminal answer — that honest refusal exists today only because nothing generates the move. v2 generates it or says why it could not.

No internal codenames anywhere near external copy. Plain function names.

For any copy it generates

Your voice gate always · plus the social gate for public posts · plus the funnel gate for sales copy · humanizer for third-party-voiced. 90 or better, or it is rewritten, never shipped. No em-dashes, no refund or guarantee language on digital products, no unverified specific numbers, first person only. A draft is never a send.

Banned in its own output

"Blocked on YOU" for anything it has not verified is actually blocked on you — that exact string caused this build. Any confident claim with no evidence string. Any spend figure without a measured or modelled label.

21The Anti-Pattern Watch

Three things this must never become. All three have already happened once in this system's history, which is why these are the ones named.

  1. It must never become a report. Two prior specs drifted toward "a better morning brief," and v4's own opening says that read was wrong. The output is an action with an owner, or a dispatch that already happened. If a release adds lines to the brief and changes nothing about what gets done, that is drift. Detector: S4. A quarter with a beautiful brief and zero dispatches is the failure.
  2. It must never become a second scoreboard. No new page, no new dashboard, no new table, no parallel ranking scheme beside the existing spine. The surface you are actually in is the chat window and your inbox. A new page is another thing to remember to look at, which is the original failure. Detector: any change adding a route, a page, or a table.
  3. It must never become an authority on truth it did not check. The failure that produced this build was a confident sentence about four things that were already done. A reasoning layer makes that failure more likely, not less, because a fluent model will happily narrate an unchecked claim. Every fact is sourced; every closure carries evidence; inconclusive is said out loud. Detector: any output sentence traceable to no source.

And a fourth, because it is the specific way a dispatching agent goes wrong: it must never ask you for approvals it already has, and never take approvals it does not. The damage list is the line. Asking above it is latency you explicitly killed. Acting below it is the incident that produced the approval-marker ban.
