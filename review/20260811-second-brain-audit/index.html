The real question: does anything read from them?

You put your finger on the thing that actually matters, so I want to answer it directly rather than bury it. A perfectly synced store nobody queries fails exactly like an empty one.

What I found

There is a read path. It was built deliberately, it works, and it has a natural-language interface. There is a retrieval engine with semantic search over the memory corpus, fused with full-text search, with section narrowing so results point at the right part of a large file. There is a skill wrapping it so a human can just ask a question.

It has zero invocation sites.

I swept the whole repo for any reference to the retrieval interface or the engine behind it. Excluding its own folder and its own test scripts, every hit is either historical (an old handoff, an absorb log, a roadmap entry) or documentation about it. There is no hook that calls it, no session-start step, no rule in any always-loaded file, and no other skill that reaches for it. The retrieval index it depends on is a gitignored local directory that is not kept in sync automatically and has to be manually refed.

So what does a lane actually do?

It greps the repo. That is the honest answer and it is well supported: every always-loaded instruction points a lane at memory/, docs/, the task board and the handoff files. Those are the surfaces that are named, that are enforced, and that are checked. The repo is the working second brain. Notion, Drive and NotebookLM are, in practice, write-only archives, and one of them is not even being written to.

This reframes the diagnosis without weakening it. You are right that things get re-derived because they were never filed where they could be found. But filing them into three stores that no lane queries would not have prevented a single one of the misses. The binding constraint is the read path. The storage path is the second problem, not the first.

The filter: which pages, and where each one goes

You said "especially ones that are important that we are looking at and using as resources," and that is the right instinct. Bulk-syncing 76 pages would make the brain worse, because a corpus of mixed-staleness documents degrades every answer drawn from it.

The filter, three tests

  1. Is it durable reference, or a snapshot? A page a future lane would need to re-read to act correctly qualifies: an offer definition, an ICP, a go-to-market plan, a playbook, a pricing decision. A status sweep, a dated audit, a one-time report does not. Ask: will this still be true in six weeks?
  2. Has it been decided? A page you have read and acted on is knowledge. An open proposal is noise, and worse, a brain full of undecided options will confidently answer with a path you rejected.
  3. Is it already the single source of truth somewhere queryable? If so, it does not get copied. The money map lives in its own database. Live decided facts live in one tracked file. Task state lives on the board. Copying those creates a second truth that will drift, and a drifted copy is worse than no copy.

One job per brain, so nothing lands in two places

The reason all three feel idle is that none of them has a job that excludes the others. Proposed division, and each page gets exactly one write to each, playing a different role:

  • Drive is the file of record. The rendered artifact you or a client would open. Immutable once filed, versioned by adding, never by editing in place.
  • NotebookLM is the ask surface. The corpus you interrogate in plain language. Strategy, research, transcripts, competitive material. This is where "what did we decide about the ghostwriting offer" should get answered.
  • Notion is the operational surface. One pointer row per filed page in the Knowledge Base: title, link, one line on what it decides, date, and status. Notion answers "what exists," the notebook answers "what does it say."

Recommendation: options, context, and the one I would take

Option A: bulk sync everything now

Push all 76 pages into all three stores this week. Cheap to say. It puts 76 documents of wildly mixed staleness into a corpus, which measurably degrades every answer it gives, and it still would not be read, because nothing queries any of it. It also risks a wrong bulk write into a brain, which is harder to undo than an empty one.

Option B: fix retrieval only

Wire one query step into the session-start path and stop there. Correct about the binding constraint, but a lane that queries a shelf holding nothing from the last three weeks gets nothing back, concludes the tool is useless, and stops using it. A read path over an empty store dies on first contact.

Option C: retrieval first, then a filtered backfill, then automate the write

Three steps in this order:

  1. Make the read path real. One step at session start, in an instruction that actually loads, that says: before claiming prior context does not exist, query the brain. Plus keep its index fed automatically instead of manually. This is the change that converts a built-and-unused tool into a used one.
  2. Backfill only what passes the three tests. Roughly six to ten pages, not 76. Small enough to be reviewed by a human before it lands.
  3. Wire the write into the chokepoint that already exists. Every review page passes through one publish script, which already refuses to ship a page that fails the layout standard. That script is the single point where filing can be made automatic rather than remembered. Same pattern as the layout gate, which worked precisely because it stopped depending on anyone remembering.
Take Option C, in that order. The reason is that the two failures are different and both real: the read path is unused, and the corpus is genuinely thin. Fixing either alone leaves the other standing. Doing the write first, which is the instinct, is the one order that definitely fails, because it is what we already did in May and it produced three stores nobody opened.

One hard blocker that needs a human

Step 3 cannot write a pointer row to the Notion Knowledge Base, because that database is not shared with our integration. No script can fix that. Someone has to open the database in Notion and connect it. Two minutes, but it gates the Notion third of the plan.
