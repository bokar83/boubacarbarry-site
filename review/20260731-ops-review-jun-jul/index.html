Backlog and intake queue:
June vs July 2026

A data-grounded comparison of how the systems backlog and the content intake queue actually performed across two months, what got measurably better, and which problems came back after they were supposed to be fixed.

Live DB queries Git history mined Council pressure-tested No estimated figures

Headline verdict

The intake pipeline got genuinely, measurably better. The backlog did not. And three named defect classes each survived the fix that was built to kill them.

Output volume was flat between the two months (2,021 vs 2,016 non-merge commits, a 0.2% difference), so this is a fair comparison and not a story about one month being quieter.

Against that flat denominator, intake processing latency fell from a 12.4-hour average to 18 minutes, and the share of records that could actually be verified as processed went from 32% to 100%. That is a real engineering win and it should be credited plainly.

The problem is on the other side. The single most damaging finding is not a count, it is a sequence: a guard was built on 2026-07-21 specifically to stop duplicate identifier allocation, and the same failure happened twice more within the following seven days, on 07-26 and 07-28. That pattern repeats across the other two worst classes. The recurring theme is that fixes are shipping as scheduled symptom management rather than cause removal, and the symptom keeps outrunning the schedule.

What this is built from

Every number below traces to a query or a git command. Nothing is estimated or recalled.

Three independent sources were used, deliberately, so that findings could be cross-checked against each other rather than resting on a single system's self-report:

  • The production Postgres database on the live server, queried directly. This covers the intake queue, the alerts table, the error table, and the new task ledger. Machine-written rows, so no narrative bias.
  • Git history, mined commit by commit. Roughly 450 commits touching the backlog file were diffed individually to detect when an item was first created versus when it first gained a closed status.
  • The backlog and board markdown files, read in full for the language people used when logging a problem, which is the only place a repeat is described as a repeat.
Reproduce these numbers yourself

The intake queue figures come from the live database, split by calendar month on the received timestamp. The backlog figures come from replaying every commit that touched the backlog file between 2026-05-01 and 2026-08-01, treating an identifier's first appearance in an added line as its creation and its first appearance alongside a closed-status token as its close.

The commit-velocity denominator is a straight count of non-merge commits in each calendar month across the whole repository. It is what makes the two months comparable, and it is the first thing to re-run if any conclusion here is challenged.

Data-quality limits, stated up front

These constraints materially weaken parts of this report. They are here at the top, not buried, because two of them were nearly presented as hard findings before review caught them.

Limit 1 · The backlog comparison is directional only, not a measurement

At the end of May the backlog file contained zero tracked identifiers. The numbering convention was introduced on 2026-06-05. That means June's 234 newly created items include the entire initial seeding of the backlog, not 234 genuinely discovered problems.

The knock-on effect is worse than it first looks. Because June was a seeding sprint, 86 of its 151 closes happened the same day they were opened, which drags June's average time-to-close down artificially. So the June-to-July shift from a 2.1-day to an 8.9-day mean is partly an artifact of how the queue was born, not purely a slowdown. Treat every backlog metric in this report as directional. The analytical weight sits on the intake database and on the confound-immune subset of the repeat analysis.

Limit 2 · July documents its repeats better than June did

Provenance notes became mandatory partway through July, and log entries got substantially more verbose. Any count of repeats derived from reading prose is therefore biased toward finding more of them in July. A raw "more recurring problem classes in July" claim cannot be separated from "July wrote them down more."

This is handled by splitting the repeat analysis into findings that survive the bias and findings that do not, and by leading only with the former. The split is shown explicitly in the repeat-incident section.

Limit 3 · Two blind spots that could not be closed

The structured task ledger only began recording on 2026-07-13, so there is no structured task data for June at all, and no clean per-lane throughput comparison is possible. Separately, the reason the error table stopped receiving writes was not established, because that would require reading the writer code, which was out of scope for a read-only review. It is reported below as an observation, not a diagnosis.

The retry ceiling is quietly burning money

Every failed record in July shares a single root cause: the analysis step returned output that could not be parsed. All 16 failures land between 07-01 and 07-08, and there have been none since, so the underlying bug was fixed. But the retry behaviour around it is still wrong, and it is still live.

Free win available now

Cap the retry ceiling at 5. The evidence is unambiguous and the change is small. On the July failure set alone this removes roughly 70 model calls that had a zero percent historical success rate, and it converts a slow permanent failure into a fast one, which surfaces the real problem sooner.

The honest reading: the same amount of work went in and less came out the other end. Commit volume was flat to within a fifth of a percent, but the proportion of created items that reached a closed state fell by nearly nine points, and the backlog grew in both months without exception.

The mean-time-to-close jump from 2.1 to 8.9 days looks alarming and is the number most likely to be misread. The median moved only from 0 to 1 day. That divergence means the typical item is still closed almost immediately, while a growing minority sit open much longer and drag the average. The backlog is not uniformly slowing, it is splitting into a fast lane and a stalled lane, and the stalled lane is growing.

Forward-looking risk: the new task ledger is already losing attribution

The structured task board that replaced hand-maintained markdown has recorded 964 tasks since 2026-07-13. 690 of them, 72%, are filed under a generic default lane rather than a real owner. Only 274 carry meaningful attribution.

This matters beyond tidiness. The reason this report has no per-lane June comparison is that structured data did not exist then. If the attribution stays at 28%, the same report next month will have structured data and still not be able to answer who did what. The instrument is being installed and miscalibrated at the same time, and it is cheap to fix now and expensive to backfill later.

Repeat incidents: the core finding

Split deliberately into findings that survive the documentation bias and findings that do not.

This was the central question, and it needs a precise answer rather than a dramatic one. A naive count says roughly 5 recurring problem classes in June against roughly 11 in July. That count is not trustworthy, for the reason set out in Limit 2: July simply wrote its repeats down more carefully. Presenting it as a headline would be the most flattering-to-the-analysis, least honest move available.

So the analysis is split. Some evidence is immune to how much prose a month produced, because it is counted from actions rather than descriptions, and that is where the real signal is.

Findings that survive the bias

1 · A guard was built, and the thing it guarded against happened twice more that week

This is the strongest single finding in the report, because a documentation habit cannot manufacture it. On 2026-07-21 a mint-time collision guard was added specifically to stop two parallel workstreams claiming the same identifier. Duplicate allocations then occurred again on 07-26 and 07-28.

The guard's own filed description concedes the hole: it only catches races that resolve in commit order before the checking lane pushes, and cannot catch two lanes that both check clean at the same moment. So this is a known-incomplete fix shipped as a complete one. The failure mode was understood at build time and the residual risk was neither closed nor flagged as accepted. Two incidents in seven days is the cost of that gap.

2 · A submodule pointer problem, fixed at the symptom at least ten times

Commits addressing this one class went from 6 in June to 26 in July, a 4.3x increase, counted from commit subjects rather than prose. The item filed on 07-16 describes itself, in its own text, as "the 8th+ near-identical occurrence." It then recurred again on 07-20 and again on 07-30.

That self-description is important for a second reason: it is a retrospective count made in July about a class that had already recurred eight times, mostly earlier. It is direct evidence that June under-reported its own repeats, which cuts against the observability confound rather than for it.

3 · A memory-cap problem declared automated in June, still failing in July

The index-size item was reclassified as automated on 2026-06-07. Interventions afterward: 11 commits in June, 13 in July. Those two numbers are close enough that the difference means nothing on its own, and it would be wrong to claim July was worse on that basis. The real finding is that the rate did not fall at all after the fix, holding at roughly three interventions a week across both months.

The fair steelman is that a scheduled trim job firing repeatedly is the automation working as designed, not failing. That defence holds for volume and breaks on correctness. In July the index was found over its own cap, a separate item recorded that 36 of 93 always-load entries were never reaching a session at all, and one intervention shows the file reaching nearly twice its cap before being cut back. The decisive evidence is organisational rather than technical: hard rules were physically relocated out of the memory system into the always-loaded configuration file precisely because the memory system could not be trusted to load them. Routing around your own component is not that component working as designed.

Findings that do NOT survive the bias

Stated plainly so they are not quietly counted twice. The following are real incidents and each is individually documented, but their concentration in July cannot be separated from July's better record-keeping, so they should not be used as evidence that reliability got worse: the background-dispatch delivery bug that recurred two days after filing, the two-disconnected-resume-systems discovery, the voice-quality regression that persisted through a retune, and the repeated merge auto-resolve content losses. The pattern underneath all three

Seven of the ten classes above are incomplete fixes or structural gaps, not discipline failures. That is the useful conclusion, because it means this is not a problem of people being careless. It is a problem of what counts as done.

In each of the three strongest cases, something shipped, was recorded as fixed, and left the actual generating mechanism in place: a check where a lock was needed, a pointer correction where a writer needed identifying, a trim schedule where a growth limit was needed. The fix reduced the symptom and the cause kept producing.

The reason this is a finding rather than a statistic is that it has already produced a confirmed failure. A logged item from 07-21 records the operator stating directly that expected notifications were not being seen. When a channel triples in volume, the messages that matter stop being distinguishable from the ones that do not, and the practical result is a notification system that is technically working and functionally ignored.

The error table went silent and nobody noticed

The dedicated error table recorded 14 rows in June and zero in July. Zero is not credible as a true value: July contained 16 pipeline failures, a container restart storm, a spend-guard shutdown, and a deploy loop. Errors demonstrably occurred.

Stated honestly, the mechanism was not verified. Establishing whether the writer was removed, renamed, or rerouted requires reading the writing code, which was outside the scope of a read-only review. What can be said with confidence is that one of the system's own error surfaces stopped producing data for a full month during which errors definitely happened, and no alert fired about the silence. A monitoring surface that can go dark unnoticed is worth one hour of investigation.

What to do about it

Ordered by evidence strength against effort. The first two are small and immediate.

  1. Cap the retry ceiling at 5. Evidence is absolute: 34 of 34 succeeded at or below 5 attempts, 0 of 12 succeeded above it. Small change, immediate model-cost saving, and it converts slow permanent failures into fast visible ones.
  2. Fix task-ledger attribution now, while the table is small. At 72% unattributed the new board cannot answer the question it was built for. Cheap at 964 rows, expensive at 10,000.
  3. Replace the identifier check with an atomic allocation. The current guard verifies and then writes, which is exactly the race it was built to prevent. A sequence or a claim-then-write in a single transaction removes the class instead of narrowing it. Two incidents in the seven days after the guard shipped are the argument.
  4. Move alert dedup to the notification layer. It is currently added per alert type, reactively, after each one floods. That design guarantees the next new alert type repeats the same incident. Volume tripling against flat workload, plus a confirmed report of missed notifications, makes this a reliability issue rather than a tidiness one.
  5. Spend one hour on why the error table went silent. Not because 14 rows a month is valuable, but because a monitoring surface went dark for a month during a period with confirmed errors and nothing noticed.
  6. Adopt a recurrence rule for closing items. This is the structural recommendation and the one that addresses the pattern rather than its instances. Any item that is the second or later occurrence of a known class cannot be closed on a symptom fix alone. It must either name the generating mechanism and remove it, or be explicitly recorded as accepted recurring with a scheduled owner. All three of the strongest findings in this report would have been caught by that rule, because in every case the incomplete fix was known to be incomplete at the time it shipped and simply was not required to say so.

Credit where it is earned

The intake pipeline improvements are real, large, and verified against machine-written data that has no narrative bias. A 41x latency reduction and closing a 68% verification gap to zero, both while signal yield more than doubled, is genuinely good engineering. The critical findings in this report are about a different part of the system and should not be read as diminishing that.
