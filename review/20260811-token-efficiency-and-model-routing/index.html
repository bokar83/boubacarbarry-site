How we manage AI usage: context size + model choice

Two related findings from the night of 2026-08-10, on one page because they're two halves of the same story. Internal working doc -- plain language, no polish pass.

TL;DR
  • The problem (measured, not guessed): every single agent dispatch pays a fixed 129,552 bytes (~32,389 tokens) of standing instructions before it reads one line of the actual task. At 401 dispatches/week that's ~13.0M tokens/week of pure overhead.
  • The root cause (the genuinely new finding): a subagent never reuses the parent session's cache -- it cold-writes that whole floor on its first call, then re-reads it every turn, on a 5-minute cache TTL. That's why cache_read was 340M of ~386M tokens in one session. It scales linearly with the floor.
  • The fix that shipped tonight, no code required: route every read-only dispatch to the Explore agent type -- it's the only kind of subagent that skips loading CLAUDE.md entirely. That alone avoids 98,715 B / ~24,679 tok per dispatch -- 76% of the floor.
  • The companion finding: a separate policy on WHICH model + how much reasoning depth to use per task. Key discovery: there is no per-call "effort" dial in the Agent tool -- reasoning depth is a session-wide setting, not something you can turn up for one hard task. The real lever is how the prompt is written.
  • Where it actually stands right now: NOT LIVE all three branches below are built, tested, and pushed -- but sitting Gate-held, waiting on your own Telegram tap. Nothing here is official until you approve it.

1. The standing context floor (measured 2026-08-10)

Every agent dispatch pays for a fixed block of content before it does any real work. Measured with scripts/context_floor_audit.py:

project CLAUDE.md          73,643 B    ~18,411 tok
user-global CLAUDE.md      25,072 B     ~6,268 tok
auto-memory index          24,400 B     ~6,100 tok   (loader cap; 7,890 B more sit on
                                                      disk and never reach an agent)
copy-battery SubagentStart  5,622 B     ~1,406 tok
task-board SubagentStart      815 B       ~204 tok
------------------------------------------------------
TOTAL FLOOR               129,552 B    ~32,389 tok

At 401 dispatches measured over 7 days, that's roughly 13.0M tokens/week spent on content that does no task-specific work.

2. Why it shows up as cache_read -- the real mechanism

The dominant line item in usage is cache_read_input_tokens -- 340M of ~386M in one measured session. That looks like "caching is working, nothing to fix." It's actually the symptom of the problem, not a reprieve from it.

Two facts about how subagent dispatches work make the math deterministic:

  1. A subagent starts its own conversation with its own cache. It does not reuse the parent's cache prefix. Its first call is a cold write of the entire 129,552 B floor.
  2. A subagent's cache uses a 5-minute TTL, even when the main session gets a full hour on the same subscription.

So each dispatch writes the floor cold, then re-reads that same prefix on every turn it takes, and anything with a gap over 5 minutes writes it cold again. In short:

cache_read  ≈  (number of dispatch turns)  ×  (size of the standing floor)

Cache reads are cheap per-token, which is why this went unnoticed for months. But the relationship to the floor is linear. Cut the floor in half, cut that entire mass in half. Turn count is the actual work happening and dispatch count is deliberately high (delegating off the main thread is the right pattern) -- the floor is the only variable actually worth attacking.

3. What does NOT work (refuted, worth recording)

These were all proposed in good faith and each is refuted by documented harness behavior. They're the ones a reasonable person tries first -- recording the dead ends matters as much as the wins.

Splitting CLAUDE.md into @imports saves nothing. The @path import syntax expands and loads imported files at launch, alongside the file referencing them. Imports are eager. A 73KB file split into six imported files is still 73KB on every dispatch.
A SubagentStart hook cannot slim anything down. The event is non-blocking, injection-only. A hook can ADD context; it cannot remove or replace what the harness already injected. Every hook in the chain is strictly additive to the floor.
Restricting a custom agent's tools: does not shrink its context. Tool restriction is enforced at runtime, not at context-load time. It's a safety control, not an efficiency one.
A "context tier" label in the dispatch prompt saves nothing. An earlier design (June 2026) proposed a CONTEXT-TIER: minimal | lean | full line on every subagent prompt, projecting a minimal agent would "skip ~6K tokens of the memory index." Wrong premise: the memory index is injected by the harness, not read by the agent, so telling an agent not to read it changes nothing about what's already loaded. The idea sat unbuilt for 64 days -- lucky, because building it would have shipped a convention with measurable cost and zero measurable benefit.

The rule that came out of this: a context-reduction idea has to name the actual mechanism that removes bytes. If it only tells an agent to want fewer bytes, it is not a fix.

4. What DOES work

Lever A -- route read-only work to Explore (the big one, shipped)

The built-in Explore and Plan subagent types skip loading CLAUDE.md files entirely (both project and user-global), to keep research fast and cheap. Every other subagent type loads both. That's 98,715 B / ~24,679 tokens avoided per dispatch -- 76% of the entire floor.

The rule: a dispatch that only reads, searches, greps, or summarizes goes to Explore. A dispatch that writes files, commits, sends, or deploys goes to a full agent.

This is the version of "context tiering" that actually works, because it maps onto a real mechanism withholding bytes rather than an instruction the agent is asked to honor.

Lever B -- pointer-ize the standing files

The test for every line in a standing instruction file: if this text vanished from the agent's context, would it VIOLATE a rule, or just lose backstory it could fetch on demand? Only backstory moves out. The directive sentence stays; the incident narrative behind it becomes a one-line pointer to a linked file.

Two structural traps found live in this repo: mirroring double-charges (rules copied from a capped memory index into the always-loaded CLAUDE.md so they don't silently drop are now in the floor twice -- a 16,083-byte block, 22% of the file, exists for exactly this reason), and a capped index still costs its cap (bytes past the loader cap reach no agent, but the bytes under the cap still bill every dispatch -- growing the index past the cap is pure loss).

Lever C -- make SubagentStart hook output conditional and short

Hooks are fully under our control. Ours currently emit ~1,610 tokens unconditionally, on every dispatch including read-only searches that will never produce a line of copy. A hook can read its stdin payload and emit nothing when the injected rule can't apply.

Lever D -- path-scoped rules for genuinely conditional guidance

Rules under .claude/rules/*.md with a paths: frontmatter key load on demand when a matching file is opened, not at startup. Real progressive disclosure -- the only such mechanism available for rule content. Note: a HARD rule that must reach every agent regardless of what it opens can't move here.

Full standing procedure + honest limits of this SOP

Standing procedure going forward

  1. Route by capability, not habit: read-only/research → Explore; writing/committing/sending/deploying → full agent.
  2. Every addition to a standing file names what it displaces. These files are a fixed budget multiplied by every dispatch, not a place to append. Adding a rule is fine; adding its four-paragraph origin story to the always-loaded copy is not.
  3. Re-measure before and after any trim: scripts/context_floor_audit.py --baseline <saved>. An unmeasured trim did not happen.
  4. Conditional guidance goes to .claude/rules/ with paths:. Always-on guidance earns its place in the floor or gets a pointer.
  5. A hook that fires on every dispatch stays short and, where possible, conditional.
  6. Re-check the floor whenever a standing file grows.

Honest limits

The skill catalog and the deferred-tool name listing are injected by the harness with no documented per-dispatch scoping control -- real weight, outside this procedure's reach. There is no documented mechanism to give a custom agent a smaller CLAUDE.md. The Explore/Plan exemption is specific to those two built-in agents, not a general capability -- any full agent still pays the full file. That's exactly why Lever B (actually shrinking the file) is unavoidable, not optional.

5. Model + effort routing policy (the companion finding)

Built the same night, in response to a related but separate ask: not "how big is the context," but "which model, and how much reasoning depth, for which task."

The headline finding: there is no per-call effort knob

Verified directly against the live tool schema, not assumed: the Agent tool takes model (sonnet / opus / haiku / fable) but has no effort, thinking, or reasoning_effort parameter at all. Reasoning depth is controlled by a single session-wide setting (effortLevel in settings.json, currently medium), which applies to every turn including trivial ones -- there's no way to dial it up for one hard dispatch without paying that cost everywhere. The actual lever for buying more reasoning depth on a specific task is how the prompt is written, not a parameter.

The matrix -- what model to use, by task type

Buying depth without an effort knob -- the actual prompt-level toolkit
  • Force a plan before action: "Before your first edit, state the change you intend and the one thing that would prove it wrong." Cheap, catches the most expensive class of error.
  • Name a verification contract: "You are done when <specific command> passes / <file> contains <thing>." Removes ambiguity that makes models over- or under-work.
  • Complete spec, then hands off (Opus 5 specifically): give it everything up front and let it run. Micro-sequencing degrades it.
  • Constrain narration and length explicitly (Opus 5 specifically): it over-narrates and writes long files by default; the effort knob doesn't fix that.
  • State scope literally: "apply this to every section, not just the first." Models don't reliably generalize an instruction across items on their own.
  • Do NOT scaffold progress updates for Sonnet 5 -- it produces them itself; old scaffolding wastes tokens.
What IS wired today: the advisory PreToolUse hook

scripts/claude-hooks/model-policy-inject.js is a PreToolUse hook on the Agent tool (confirmed firing on real dispatches tonight). PreToolUse is the right event because it fires before the dispatch, while the model choice is still changeable -- unlike SubagentStart, which fires after the model is already bound.

What it does: classifies the dispatch prompt with keyword heuristics into trivial/triage, code, or high-stakes; injects a short advisory only when the model choice looks actionable (a code/high-stakes dispatch pinned below the floor, or a plainly trivial dispatch not using haiku); stays silent otherwise, which is deliberate -- most dispatches produce zero injected tokens so this doesn't fight the parallel context-size effort.

What it honestly cannot do: change the model. PreToolUse gives an allow/block/inject shape, not a rewrite-the-arguments shape. It reminds; the dispatcher still decides. It never blocks -- a keyword heuristic can't be trusted to brick a dispatch.
