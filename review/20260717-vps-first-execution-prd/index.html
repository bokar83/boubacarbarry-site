Move the work to the machine that never sleeps

Shift the majority of agentic work off the laptop CLI tabs and onto the always-on server, triggered by a text message, using the subscriptions already paid for.

1

The end-state, in plain terms

▾

Today, the open-ended agentic work — building websites, writing content, fixing agentsHQ itself — only happens while the laptop is on and a terminal tab is open per model lane. Close the lid, work stops.

The goal: the laptop becomes a thin remote control, not the engine. A text message to the bot on the server kicks off the same range of work — and the right model picks it up, runs it on the server, and reports back — whether the laptop is open, closed, or in another country. Crucially, that work should run on the subscriptions already paid for (the Claude, Gemini, and ChatGPT/Codex plans), not on per-call metered billing. Metered calls stay as a fallback only, for the narrow cases where a subscription path will not work.

What must not change: the server's own internal crews keep making metered calls through the existing gateway (that hard rule is untouched), and nothing gets merged into the live system or deployed without the existing approval gate — a human still signs off on anything high-risk.

One-line verdict: The destination is reachable and mostly worth it. Two of the three model tools have a clean, documented way to log in and run unattended on a server today. The third (the primary one) has a known unattended-login bug that caps how long a single job can run before it needs a fresh token. So the plan ships in phases, with that bug treated as a first-class constraint, not a footnote.

4

Proposed architecture

▾

Additive, not a rewrite. The existing Gate + scheduler + agent bus stay exactly as they are. One new component (a CLI worker + a router in front of it) is bolted on, and it produces feature branches that flow through the same Gate every other lane already uses.

  Boubacar's phone
        |  "build a landing page for X" / "fix the gate bug" / "draft 3 posts"
        v
  [ Telegram bot @CCagentsHQ_bot ]
        |  webhook -> existing orchestrator app.py
        v
  [ DISPATCHER / ROUTER ]  (new, thin)
     - classify job: website-build | content | self-fix | research
     - pick tool+model: Codex/agy for long runs, Claude for short bounded
     - create git worktree off origin/main, write a job row in postgres
        v
  [ CLI WORKER POOL ]  (new systemd unit or sidecar container on VPS)
     - claude -p   (CLAUDE_CODE_OAUTH_TOKEN, short runs + refresh watchdog)
     - codex exec  (device-auth token)
     - agy         (SSH-OTP token, auto-renew)
     - runs INSIDE the worktree, commits [WIP] early + often
     - job-id <-> session-id map in postgres  (= server-side lane marker)
        v
  [ RESULT ] -> agent_comms bus + Telegram notifier  (existing)
        |
        v
  [ GATE (gate_agent.py) ]  UNCHANGED, still the SOLE merger
     - [READY] branches auto-merge; [WIP] skipped
     - Tier-C / HIGH_RISK  -> Boubacar's explicit approval, never auto-merged
        v
  [ safe_pull.sh on VPS ] -> live

  Orchestrator's own crews -> OpenRouter gateway  (UNCHANGED hard rule)
  Subscription-CLI path is NEW and additive; OpenRouter = fallback only.

Five load-bearing decisions baked in:

  • Tokens live in .env (git-ignored, never printed), mounted to the worker. Named, never valued, in any output.
  • The worker writes only inside a worktree off origin/main — never the canonical VPS tree, never /root/agentsHQ directly. This respects the read-only-VPS-tree rule; work reaches live only through Gate + safe_pull.sh.
  • Gate stays the one human checkpoint. The worker cannot merge or deploy. It can only push a branch, exactly like a spawned coding agent today.
  • Session persistence = a postgres job-id→session-id row, the direct server-side equivalent of the cc-lane-resume marker file, so a long job resumes its exact CLI session (claude --resume / codex resume / agy resume).
  • Reuse the bus. Results go back over the existing agent_comms + Telegram notifier — no parallel reporting system invented.
Relationship to the planned self-healing agent (Hermes): this worker is the general-purpose sibling of that already-planned, write-boundary-locked agent. It should inherit the same allowlist/forbidden-path model (no writes to CLAUDE.md, AGENTS.md, .env, gate_agent.py, orchestrator/*.py without Gate review) rather than invent a second, looser boundary. Recommend: one shared write-boundary enforcement layer, two callers.
5

Council: 5-angle stress test

▾
1 · The Contrarian

The premise leans hardest on the one tool that is broken for this exact use.

The whole pitch is "run it unattended on the server." Claude Code — the primary, most-used tool — drops a 401 after 10–15 minutes in non-interactive mode because it will not refresh its own OAuth token (issue #28827, still open). A website build or a real self-fix is rarely a 10-minute job. So for the marquee use case, on the marquee tool, the naive version of this plan simply fails a third of the way through, silently, and the branch never appears. A skeptic says: you are moving work from a place where it completes to a place where it dies mid-run unless you build a babysitter first.

2 · The First-Principles Thinker

The real question is not "can a CLI run on a server" — it is "what is the unit of work being moved."

Strip it down. The deterministic, cron-shaped work is already on the server. What is laptop-bound is open-ended model sessions. The right frame is not "port 8 terminal tabs to the cloud." It is: "which jobs are actually long-running-autonomous, and which are just Boubacar thinking out loud with a model?" The second kind should stay interactive (they need him in the loop anyway). Only the first kind — a fully-specified build or fix with a machine-checkable done-condition — belongs on the unattended worker. Move the PRD-shaped jobs, not the conversations. That reframing shrinks the build and sidesteps most of the Claude-401 problem, because well-specified jobs can be chunked into sub-15-minute runs.

3 · The Expansionist

The dispatcher is worth more than the worker.

The undersold asset here is the router. Once a text message can be classified and routed to "the right model for this job," you have a model-arbitrage layer: cheap long jobs to the auto-renewing Gemini/Codex tokens, high-taste jobs to Claude, metered fallback only when a subscription is saturated. That same router can later dry-run cost estimates, load-balance across the three subscriptions to dodge each one's rate cap, and become the front door for every agentic request, not just CLI jobs. Build the router as a first-class, reusable service, not a glue script buried in app.py.

4 · The Outsider

A stranger cannot tell this apart from a botnet running one login eight ways.

Cold read: someone is taking a single consumer subscription and fanning it into 8 concurrent unattended headless workers on a rented server. Every provider's ToS is written for one human at a keyboard. Nobody has confirmed that 8-way concurrent server-side automation off one Max seat is inside the intended-use line — the plan just assumes it. The outsider also notices there is no answer to "what happens when a provider flags the account and suspends it" — that would take down not one lane but the entire moved workload at once. Concentration risk that an insider waves away because "it works today on the laptop."

5 · The Executor

Do not build the pool first. Build one worker, one tool, one job type, and measure the token wall.

The exact next move: stand up a single Codex codex exec worker on the VPS (the tool with the cleanest headless-subscription path and no refresh bug), wired to accept exactly one job type (a fully-specified website build) via one Telegram command, producing a [WIP] branch through the existing Gate. Ship that end-to-end before touching Claude or Gemini or concurrency. If it does not clear a real build inside one week, the multi-tool pool is premature. Timing: this is a phased de-risking spike, not a platform launch — if Phase 0 is skipped and the full pool is built first, the Claude-401 and ToS-concentration risks land all at once in production.

Chairman synthesis — forced verdict: BUILD, but phased and re-scoped. The genuine tension the council surfaced: the Contrarian and Outsider want to slow down (broken primary tool + unproven ToS posture), while the Expansionist wants to go bigger (the router is the real prize). Both are right, and the First-Principles reframe resolves it: move only PRD-shaped autonomous jobs, start with the one tool that actually works headless (Codex), build the router as a real service, and treat the Claude-401 bug and the single-subscription concurrency question as gating unknowns, not details. The sharpest truth: the value is not "CLI in the cloud," it is "a model-router that survives the laptop being off" — and the fastest way to kill this project is to build the 8-way pool before proving one worker clears one real job.

Note: Voices split on pace — Contrarian/Outsider (de-risk first) vs Expansionist (build the bigger router now). That tension is real and is resolved in the plan by phasing: Phase 0 proves one worker; the router graduates to a service only after.

6

Karpathy: 10-principle audit

▾

Audited as a design/PRD, not shipped code. Principles that can only be judged at implementation time are marked WARN with the guardrail the build must honor.

P1 Think before codingPASS Intent stated, hidden assumption (headless subscription auth) was verified against fetched docs before any design, not assumed.
P2 Simplicity firstWARN The full 3-tool pool + router + session-store is more than the problem needs on day one. Action: Phase 0 = one tool, one job type, no pool. Do not build the abstraction for 3 tools until 1 works.
P3 Surgical changesPASS Additive by design — Gate, scheduler, bus, and the OpenRouter rule are untouched. The worker is a new unit that pushes branches like any existing agent.
P4 Goal-driven executionWARN "Done" per dispatched job must be machine-checkable or the unattended worker cannot know it succeeded. Action: every job row carries an explicit done-condition (build passes / branch pushed / test green) before the worker starts.
P5 Complexity hotspotsPASS (report-only) No hot loops. Watch the router classifier for per-request LLM calls — keep classification cheap/rules-first before reaching for a model.
P6 VerificationWARN The Claude-401 failure must be reproduced on the VPS and covered by a watchdog test before Claude is trusted for any job >10 min. Action: Phase-gate Claude behind a token-refresh watchdog with a passing re-mint test.
P7 Debugging protocolPASS The known failure was read to its root (non-interactive refresh, not "auth is flaky") from the actual issue, and the design changes one variable (Codex-first) rather than blaming the whole approach.
P8 DependenciesPASS No new packages — reuses git, postgres, systemd/docker, the existing bus + notifier, and the three CLIs already installed. New surface is config + one service, not a dependency tree.
P9 CommunicationPASS Uncertainty is labeled, not smoothed: Claude headless = "viable with caveat," the single-subscription concurrency ToS question = flagged as an open unknown, not asserted safe.
P10 Failure modesWARN Two lurking patterns: Optimistic Path (assuming Claude runs to completion — it will 401) and Kitchen Sink (building the 8-way pool before one worker proves out). Action: the phased plan below exists specifically to hold both at bay.
FINAL CALL: SHIP the PRD, HOLD the full build. No core principle FAILs — the design is honest and additive. But four WARNs (P2, P4, P6, P10) all point at the same discipline: do not build the pool first. The gating actions before any multi-tool build: (1) Phase 0 proves one Codex worker end-to-end; (2) every job carries a machine-checkable done-condition; (3) Claude is phase-gated behind a reproduced-and-tested token-refresh watchdog; (4) the single-subscription concurrency + ToS question gets a human answer before fan-out.

7

Execution plan (ordered, buildable steps)

▾

Each step names what gets built, where it lives, how it is verified, and an effort tier (S = <half day, M = 1–2 days, L = 3–5 days). A coding agent can pick these up one at a time. Nothing here is authorized to build yet — this is the plan Boubacar reviews first.

Phase 0 — One worker, one job, prove the loop (de-risk)

  1. [S] Mint + store the Codex subscription token on the VPS. Run codex login --device-auth in an SSH session, complete the device code on the laptop browser. Store the resulting token in .env (never committed). Verify: codex exec "print hello" returns from the VPS with the laptop closed.
  2. [M] Build a single-job worker script. Lives at orchestrator/cli_worker.py (Gate-reviewed, since it is orchestrator code). Takes a job spec, creates a worktree off origin/main under agentsHQ-worktrees/, runs codex exec inside it, commits [WIP] early + often, pushes the branch. Verify: a hand-fed job spec produces a pushed branch the Gate then processes.
  3. [S] One Telegram command → one job. Extend the existing bot handler in app.py so a single command (e.g. /build <spec>) writes a job row and invokes the worker. Verify: a phone message with the laptop off yields a branch + a Telegram result reply.
  4. [S] Measure the token wall. Run 5 real builds; record how close the account gets to its 5-hour-window and weekly caps. Verify: a short data note Boubacar can read to decide the tier question (see §9).
Phase 0 gate: if one Codex worker cannot clear a real website build end-to-end in a week, stop — the pool is premature. Only proceed past here on a clean Phase-0 pass.

Phase 1 — The router as a real service

  1. [M] Job-classification + model-routing service. A small module orchestrator/dispatcher.py: rules-first classification (website-build / content / self-fix / research) → tool+model choice. Cheap heuristics before any LLM call. Verify: a fixture set of 20 sample requests routes to the expected tool with a logged rationale.
  2. [M] Postgres session-persistence table. cli_jobs(job_id, tool, session_id, worktree, status, done_condition, created_at) — the server-side equivalent of the lane-marker file. Verify: a job killed mid-run resumes its exact CLI session via the stored session-id.
  3. [S] Machine-checkable done-conditions. Every job row must carry an explicit success test (build passes / tests green / branch pushed) set at dispatch. Verify: the worker refuses a job with no done-condition.

Phase 2 — Add Gemini/agy (auto-renew tool), then Claude (gated)

  1. [S] Add the agy worker. agy SSH-OTP login on the VPS; token auto-renews. Wire as a second worker backend behind the router. Verify: a content job routes to agy and completes with the laptop off.
  2. [M] Claude worker behind a token-refresh watchdog. Reproduce the 401 on the VPS first (P6). Build a watchdog that detects the 401, re-mints/re-injects CLAUDE_CODE_OAUTH_TOKEN, and resumes the session; cap individual Claude runs to sub-15-minute chunks. Verify: a >30-minute Claude job completes across at least two token cycles without manual touch.
  3. [S] Reuse one write-boundary layer with the planned self-healing agent. The worker inherits the existing locked allowlist/forbidden-path model (no CLAUDE.md/AGENTS.md/.env/gate_agent.py/orchestrator writes without Gate review). Verify: a job that tries to write a forbidden path is blocked pre-commit.

Phase 3 — Concurrency + hardening (only after ToS answer)

  1. [M] Controlled fan-out. Allow N concurrent workers only after the single-subscription concurrency/ToS question (§8) has a human answer. Router load-balances across the three subscriptions to stay under each rate cap; metered OpenRouter is the documented fallback when a subscription is saturated. Verify: concurrent jobs stay under caps and fall back cleanly, logged per-source.
  2. [S] Account-suspension blast-radius guard. Detect an auth-suspension on any subscription and alert + fail over, so one flagged account does not silently take down the whole moved workload. Verify: a simulated auth failure triggers alert + fallback, not a silent stall.

9

Claude Max: $200 (20x) vs $100 (5x)

▾

Recommendation: insufficient data to downgrade — hold at $200 (20x) through Phase 0, then decide from measured usage. I will not fabricate a token/dollar figure I cannot observe.

What the public limits say (2026): Max 20x ($200/mo) ≈ 900 messages per rolling 5-hour window and ~240–480 Claude Code hours/week; Max 5x ($100/mo) ≈ 225 messages per 5-hour window and ~140–280 hours/week; both plans additionally throttle after ~50 sessions/month, and a weekly cap sits behind the 5-hour cap.

What I can observe: Boubacar runs roughly 8 concurrent lanes today. Consolidating that — plus more moved work — onto one account pushes usage up, toward the 20x envelope, not away from it. That is an argument against downgrading right now.

What only Boubacar can check (his billing dashboard, not visible to me):
  • Settings → Usage: how often he currently hits the 5-hour-window cap and how close he runs to the weekly cap on the existing 8-lane load.
  • Whether he is near the ~50 sessions/month throttle already.
If he is routinely under ~50% of the 5-hour and weekly caps today, $100 (5x) may be safe after the reframe moves long jobs onto the auto-renewing Codex/Gemini tokens (which offload Claude). If he is already brushing the caps, moving more work onto the account means stay at $200.

Phase-0 step 4 ("measure the token wall") produces exactly the data to settle this — decide the tier from that, not from a guess.
