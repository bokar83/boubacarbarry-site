Product Requirements + Execution Plan

Move the work to the machine that never sleeps

Take the way we already work back and forth, and lift it off the laptop into the cloud, without losing memory, without confusion when several requests land at once, and without weakening the human sign-off on anything risky.

Prepared 2026-07-17 · Research + PRD only, no build this run · Read-only VPS inspection + this-session web citations + 3 parallel prior-art research agents · Tap any section header to collapse.

1

The end-state, in plain terms

▾

In your own words: you want to take the way you and an AI assistant work back and forth — asking questions, saving memory where you left off, continuing from there — and do the exact same thing inside your own system, run from the cloud, not tethered to your laptop or any one physical place. Still secure. Still remembering. Not getting lost or confused when three to five requests arrive at once from different places.

So the bar is not just “the server can run jobs.” It is conversational-session parity, cloud-native — the full §2 North-Star. Today the deterministic scheduled work already runs on the server unattended; what dies when the laptop closes is the open-ended, back-and-forth model work. This plan moves that, in phases, and is honest about which parts are reachable soon versus which are the long pole.

One-line verdict: Reachable, and most of the hard parts have existing parts to reuse rather than invent. Concurrency-safety reuses infrastructure you already run; persistent memory has a drop-in library that fits your exact database; the human sign-off stays exactly as it is. The genuinely hard, further-out piece is true interactive back-and-forth mid-task — that is the north-star's long pole, named plainly in the plan, not quietly scoped away.

This is the second, expanded version of this PRD. It adds the North-Star bar (§2), a prior-art reuse map from three parallel research agents (§5), and a plan that tags every step as parity-prerequisite versus execution-offload plumbing (§9).

2

North-Star success criteria: CLI-session parity, cloud-native

▾

This is the real bar. Your explicit caveat is that it is not achievable today or in 24 hours — it is the destination the plan aims at. Four criteria, and an honest read of how far the proposed architecture gets toward each.

CriterionWhat it meansHow far the plan gets
1. Conversational continuity A cloud session (via Telegram, web, API) supports genuine back-and-forth — it can ask a clarifying question, get an answer, and keep reasoning across turns. Not fire-and-forget dispatch. PARTIAL — the long pole The building block exists (the model CLIs keep a session ID and can resume it), but turning fire-and-forget dispatch into a real interactive loop that pauses, asks you a question in the channel, waits, and resumes is the hardest piece and the furthest out. Named as the north-star long pole, not solved this pass.
2. Persistent memory across time The cloud equivalent of the memory system + “pick up where we left off,” addressable without a laptop-resident session file. BUILDABLE — mostly reuse A drop-in memory layer (mem0) runs on the Postgres you already have and the orchestrator framework already supports it; a small thread-keyed state table gives resumable “where we left off.” Closest of the four to a wholesale adopt.
3. Concurrency-safe 3–5 simultaneous requests from different people/places must not corrupt or cross-contaminate each other's state. A real distributed-systems requirement. SOLVABLE — existing infra Scope every conversation by a composite key, and serialize per-conversation writes with a lease. The system's existing claim/complete coordination table already is that lease primitive. Add a small dedupe table for repeated inbound events. Little new infrastructure.
4. Security preserved Cloud-native must NOT loosen the human-checkpoint model (the merge gate; explicit approval for high-risk changes). PRESERVED Session parity is about conversation + memory, not merge authority. The worker only ever pushes a branch; the Gate stays the sole merger; high-risk paths still need your explicit approval. Reconciled explicitly in §6.
Honest overall: the plan reaches execution-offload, concurrency-safety, and persistent-memory using mostly-existing parts. It does not fully reach criterion 1 (true interactive back-and-forth mid-task) in this scope — that is the north-star's long pole and is called out as such in the plan (Phase 4) and the open questions (§10). Criteria 2–4 are the near-term wins; criterion 1 is the horizon.

B. Laptop-only (dies when the lid closes) — the migration target

One launcher per model lane opens a terminal tab running a CLI (Claude Code, Codex, or Antigravity/Gemini) with a lane charter appended. Session continuity is a per-lane marker file: it walks up the process tree to read the live CLI's own resume argument, so it re-attaches the exact session. The gap in one sentence: the server can already schedule and merge deterministic work unattended; what it cannot yet do is hold an open-ended, resumable conversation that builds a site, writes a post, or fixes a bug without a human-held terminal — and do it safely when several land at once.

Concurrency-safety (the “3–5 at once” requirement) — existing infra wins

  • Composite session key (channel:chat_id:thread) is the isolation primitive — it becomes the primary key of a conversations table and the routing key on the message bus. Different people/channels resolve to different rows: zero shared state.
  • Serialize same-conversation turns with a lease. The system's existing claim/complete coordination table already is a Postgres lease/mutex: claim('conversation:<key>', worker, ttl) before a turn; if held, enqueue on the bus instead of running. This is a lateral-leverage win — the lock already exists.
  • Idempotency table (INSERT ... ON CONFLICT on the provider message-id) dedupes repeated inbound events so a retried webhook never spawns a second run.

Claude Agent SDK: what session-resume gives vs what must be built

The SDK auto-persists each conversation as a transcript on disk and exposes a session ID with --resume / --continue / fork. It does not give multi-tenant routing, per-conversation locking, a shared-DB session store, or event dedupe — those are the layer to build. Cross-host resume is fragile because the SDK keys its local transcript by working directory, so a horizontally-scaled server must pin a conversation to one host or shuttle+rehydrate the transcript.

Telegram-to-cloud-agent pipelines that already shipped

Three real repos converge on one architecture: a single daemon with per-chat session state in a small database, plus an anti-contamination trick — either batch rapid messages into one prompt, or isolate each agent in its own container with an independent session (one caps at 3 concurrent). An internal Telegram-inbound module is already a prior PROCEED, so the trigger front door is not greenfield.

Net: adopt mem0 for memory; port the thread-keyed checkpoint pattern for resumable state; reuse the existing claim/complete table + a new idempotency table for concurrency-safety; reuse the existing Telegram-inbound module for the trigger. The only genuinely new, hard build is the interactive back-and-forth loop (criterion 1).

Proposed architecture

▾

Additive, not a rewrite. The existing Gate + scheduler + message bus + coordination table stay as they are. A new worker + router is bolted on, and every job it produces flows through the same Gate every other lane already uses.

Load-bearing decisions:

  • Tokens live in the environment file (never committed, never printed), mounted to the worker.
  • The worker writes only inside a worktree off the main line — never the live server tree directly. Work reaches production only through the Gate.
  • The Gate stays the one human checkpoint. The worker can only push a branch, exactly like a spawned coding agent today. This is how criterion 4 (security) is preserved without weakening anything.
  • Concurrency-safety = composite key + existing lease + idempotency table (criterion 3), reusing infrastructure already running.
  • Memory = mem0 + a thread-keyed checkpoint table (criterion 2), the server-side equivalent of the laptop's marker file.
Relationship to the planned self-healing agent: this worker is the general-purpose sibling of the already-planned, write-boundary-locked self-healing agent. It should inherit the same allowlist/forbidden-path model (no writes to the SOP files, environment file, gate, or core orchestrator source without Gate review) rather than invent a second, looser boundary. Recommend one shared write-boundary enforcement layer, two callers.
7

Council: 5-angle stress test

▾
1 · The Contrarian

The premise leans hardest on the one tool that is broken for this exact use.

The whole pitch is unattended-on-the-server, and the primary tool drops a 401 within ~10–15 minutes headless and dies every ~8h on cron — confirmed across six separate bug reports, not one flaky anecdote. A real build or fix is rarely a 10-minute job. So on the marquee tool, the naive version fails a third of the way through, silently, and the branch never appears. You are moving work from a place where it completes to a place where it dies mid-run unless you build the watchdog first.

2 · The First-Principles Thinker

The unit of work being moved is not “a terminal tab” — it is a conversation.

Strip it down. Deterministic work is already on the server. What is laptop-bound is open-ended model conversations. The north-star makes this explicit: the thing to reproduce is the back-and-forth, the memory, the resume — not just command execution. That reframes the whole build. Execution-offload (run a job, push a branch) is the easy half and mostly a plumbing problem. Session parity (remember, resume, converse, stay isolated under load) is the real half, and it is a state-management problem, not a CLI problem. Build the state layer deliberately; do not let “it runs jobs now” masquerade as “it works like we do.”

3 · The Expansionist

Most of the hard layer is already sitting in the codebase.

The undersold assets: the coordination claim/complete table is already a per-conversation mutex; the message bus is already a per-lane ordered mailbox; Postgres+pgvector already runs, and the memory library that fits it is one the orchestrator framework already supports; the Telegram-inbound module is already a prior PROCEED. The parity layer is less “build a distributed system” and more “wire four things you already own into a conversation spine.” That same spine later becomes the front door for every agentic request, and a model-arbitrage layer (cheap long jobs to the self-refreshing tokens, high-taste jobs to Claude, metered only when saturated).

4 · The Outsider

A stranger cannot tell this apart from one login fanned eight ways — and now there's evidence it breaks.

Cold read: a single consumer subscription fanned into many concurrent unattended workers on a rented server. Every provider ToS is written for one human at a keyboard. And this is no longer just a worry — a real report shows 5–6 concurrent instances on the top tier hitting infrastructure rate-limiting that makes sustained multi-instance use “effectively non-viable,” because limits pool across the account. So the concurrency dream collides with a measured wall. No account bans were found in the sources, but throttling alone is enough to break the promise if the design assumes free fan-out.

5 · The Executor

Build the conversation spine on one self-refreshing tool first; prove memory + isolation before Claude and before fan-out.

Exact next move: stand up ONE Codex worker (self-refreshing tokens, no 401 bug) behind the existing Telegram-inbound module, wired through the idempotency table + a composite conversation key + the existing claim/complete lease, producing a [WIP] branch through the Gate — and attach mem0 on the existing Postgres so the second message in a thread remembers the first. That single vertical slice proves criteria 2, 3, and 4 at once on the tool that actually works headless. Only then add Claude (behind a token watchdog), then agy, then — last, and only after the ToS answer — concurrency fan-out. Do not touch the interactive-clarifying-question loop (criterion 1) until that slice is solid; it is the long pole, not the starting point.

Chairman synthesis — forced verdict: BUILD, phased, spine-first. The tension: Contrarian and Outsider want to slow down (broken primary tool + a measured concurrency wall), while the Expansionist sees most of the hard layer already in the repo. The First-Principles reframe resolves it — the thing being moved is a conversation with memory and isolation, and three of its four pieces reuse infrastructure that already exists. So: prove the conversation spine (memory + isolation + Gate) on Codex first, add the other tools behind their specific caveats, treat concurrency fan-out as gated on a real ToS answer, and treat interactive back-and-forth as the horizon, not the sprint. Sharpest truth: the value is not “CLI in the cloud,” it is “our way of working, with memory, that survives the laptop being off and does not get confused under load” — and the fastest way to kill it is to chase all eight lanes concurrently before one conversation resumes correctly.

Note: Voices split on pace — Contrarian/Outsider (de-risk first) vs Expansionist (the parts are already here, move). Resolved by spine-first phasing: one vertical slice proving memory + isolation before any fan-out.

9

Execution plan (ordered, tagged parity vs plumbing)

▾

Each step names what gets built, where, how it is verified, and an effort tier (S=<half day, M=1–2 days, L=3–5 days). Tags: PARITY moves toward the north-star (conversation / memory / concurrency); PLUMBING is execution-offload only. Nothing here is authorized to build yet.

Phase 0 — One worker, one job (de-risk execution)

  1. PLUMBING [S] Mint + store the Codex subscription token on the VPS. codex login --device-auth over SSH; token in the environment file. Verify: codex exec "print hello" returns from the VPS with the laptop closed.
  2. PLUMBING [M] Single-job worker script. Gate-reviewed (it is orchestrator code). Takes a job spec, creates a worktree off the main line, runs codex exec, commits [WIP] early + often, pushes. Verify: a hand-fed spec produces a pushed branch the Gate then processes.
  3. PLUMBING [S] One Telegram command → one job via the existing inbound module. Verify: a phone message with the laptop off yields a branch + a Telegram reply.
  4. PLUMBING [S] Measure the token wall. Run 5 real builds; record proximity to the 5-hour-window and weekly caps. Verify: a short data note for the tier decision (§11).

Phase 1 — Concurrency-safety foundation (criterion 3)

  1. PARITY·concurrency [S] Idempotency table. idempotency_keys in Postgres, INSERT ON CONFLICT on provider message-id at ingress. Verify: a duplicated inbound event spawns exactly one run.
  2. PARITY·concurrency [M] Composite conversation key + per-turn lease. Resolve inbound to channel:chat_id:thread; claim('conversation:<key>', worker, ttl) via the existing coordination table before a turn; contended turns queue on the bus. Verify: two overlapping turns on one key never interleave; different keys run in parallel untouched.
  3. PLUMBING [M] Router + machine-checkable done-conditions. Rules-first job classification → tool choice; every job row carries an explicit success test. Verify: 20 sample requests route as expected; a job with no done-condition is refused.

Phase 2 — Persistent memory (criterion 2)

  1. PARITY·memory [M] Adopt mem0 on the existing Postgres/pgvector as the orchestrator's external-memory provider, scoped per conversation key. Verify: the second message in a thread recalls a fact from the first, with the laptop off; a different key cannot read it. (License confirmed + version pinned first.)
  2. PARITY·memory [M] Thread-keyed checkpoint table (cli_jobs: job/session id, tool, worktree, status, done-condition), the server-side marker-file equivalent. Verify: a job killed mid-run resumes its exact CLI session from the stored id.

Phase 3 — Add tools + preserve the gate (criterion 4)

  1. PLUMBING [S] Add the agy worker (one-time SSH-OTP, then auto-renews) as a second backend behind the router. Verify: a content job routes to agy and completes, laptop off.
  2. PLUMBING [M] Claude worker behind a token-refresh watchdog. Reproduce the 401 on the VPS first; watchdog re-mints the token on a cron and resumes; cap Claude runs to sub-15-min chunks. Verify: a >30-min Claude job completes across two token cycles with no manual touch.
  3. PARITY·security [S] Share one write-boundary layer with the planned self-healing agent. Worker inherits the existing allowlist/forbidden-path model; Gate stays sole merger; high-risk needs explicit approval. Verify: a job that tries to write a forbidden path is blocked pre-commit; a high-risk branch is never auto-merged.

Phase 4 — Conversational continuity (criterion 1, the long pole)

  1. PARITY·conversation [L] Interactive back-and-forth loop. Let a worker pause mid-job, post a clarifying question back to the channel, await a reply, and resume the same session with full context (built on the Agent SDK's resume + the checkpoint table + the conversation lease). Verify: a job that hits an ambiguity asks you a question in Telegram, waits, and continues correctly after your reply, laptop off. This is the north-star's hardest piece; expect it to need its own PRD + iteration beyond this plan.

Phase 5 — Concurrency fan-out + hardening (only after a ToS answer)

  1. PARITY·concurrency [M] Controlled fan-out. Allow N concurrent workers only after §10 Q1 is answered. Router load-balances across the three subscriptions to stay under each cap; metered fallback when a subscription is saturated. Verify: concurrent jobs stay under caps and fall back cleanly, logged per-source.
  2. PLUMBING [S] Account-suspension blast-radius guard. Detect an auth suspension on any subscription and alert + fail over. Verify: a simulated auth failure triggers alert + fallback, not a silent stall.
Read of the ordering: Phase 0 is pure plumbing (prove execution). Phases 1–2 are the parity core (isolation + memory) and reuse existing infra. Phase 3 adds tools and locks in the security criterion. Phase 4 is the long pole. Phase 5 is gated on your ToS decision. The spine (Phases 0–2) is where the real value lands early.

Claude Max: $200 (20x) vs $100 (5x)

▾

Recommendation: insufficient data to downgrade — hold at $200 (20x) through Phase 0, then decide from measured usage. No fabricated token/dollar figure.

Public limits (2026): Max 20x ($200/mo) ≈ 900 messages per rolling 5-hour window and ~240–480 Claude Code hours/week; Max 5x ($100/mo) ≈ 225 messages per 5-hour window and ~140–280 hours/week; both throttle after ~50 sessions/month, with a weekly cap behind the 5-hour cap.
