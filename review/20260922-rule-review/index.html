2026-09-22 · six decisions below, plus a strike list you can adjust · nothing has been applied yet

0. The finding, plain

You asked: with 290+ rules, does the newer Claude Code still need all of them, or did the model get good enough that some can go? The honest answer: almost none are obsolete because the model changed. Only 3 of 375 rules are wrong because Claude Code itself changed (they all claim a task-list tool "does not exist" — it does now, just off by default). The other 64 archive candidates were never really rules: old handoffs, prices and dates that changed, one-off facts, expired time windows.

The real problem isn’t staleness, it’s volume and delivery. You are carrying:

375always-load rows
~107 KBtext loaded every session
20already backed by a real hook
54startup processes/session
~25rows in the proposed core
10new/extended hooks proposed

The plan: keep a small core of the rules that are genuinely every-session and high-stakes (damage list, send gate, never touch the deploy tree, never write a gate-approval file, model floor, and similar). Turn what a computer can enforce into 10 hooks — not 290, not one per rule. Move the rest into topic files that only load when you’re actually touching that topic (Money Map rules only load when someone’s editing the Money Map, review-page rules only when someone’s building a review page, etc). Archive what was never really a rule — old handoffs, prices, one-off facts — but never delete it, just stop loading it every time.

Nothing below has been touched yet. This page is where you decide; the six choices below cover everything that matters.

Six decisions

Approve = go with the recommendation. Reject = keep it as-is / pick a different option (say why in the note — agents read it). Park = revisit later. Nothing here applies itself; these just record what you want done.

D1. How you approve the cuts — by category, or row by row?

By category, with this strike listRecommended
You review 8 category buckets (counts, not all 375 rows) and the strike-list below. Per-row approval of 180+ rows realistically never happens and stalls everything.

D2. How many new hooks — 10 total, or something else?

5 new + 5 extended (10 touches total)Recommended
Each hook covers a whole CLASS of violation (every outbound send, every dark-background page, every destructive command shape) — not one hook per rule. This is the floor: fewer than this and a whole class goes unguarded.
One hook per rule (290 hooks)
The outcome you already rejected — unmaintainable, and defeats the point of simplifying.

D3. Example cut: 13 "fix it, don’t ask" rules → 1 line

Consolidate to one lineRecommended
13 separate always-load rules, written on 13 different dates, all say the same thing: find a problem, fix it, report the fix, don’t ask permission. That’s not 13 rules — it’s one rule that got re-written each time it was broken instead of enforced once. Becomes one T0 line: "a found problem is a fixed problem; ask only on the damage list." The 13 incident dates stay in their own memory files, just not loaded every session.
Keep all 13 separately
Keeps every incident date visible in the core, at the cost of the core staying bloated. This one example is representative of ~90 similar agent-conduct rows.

D4. Move your 6 global HARD-rule sections into the repo file?

Move into the repo CLAUDE.mdRecommended
Your global ~/.claude/CLAUDE.md lives on your laptop and the Huawei, outside the repo — no branch, no review, no Gate, and it has to be hand-edited identically on two machines. Moving its 6 HARD sections into the repo file means one home, one diff, one Gate review, and both machines read the same source through Git instead of a manual copy.
Leave the global file as-is
Keeps the split, keeps the two-machine hand-sync risk, and keeps that file outside your own Gate review process.

D5. Publish this kind of review page as the standard way you review rule changes?

Yes, this is the pattern going forwardRecommended
You said you don’t read .md files, so a 350-line proposal document was never going to be what you actually review. This page (summary + decisions + collapsible detail + a strike list you can adjust) is the format that works on your phone and saves your choice to a real database, not a file.
Something else
Say what format you’d rather see this kind of review in.

Archiving means the file stays in memory/ forever (nothing is ever deleted) — it just stops loading every session. This can happen this week, independent of everything else on this page.
Wait, do it together with the rest
Bundles it into the bigger, slower decision.

The 3 rows that are actually wrong because Claude Code changed

These claim a task-tracking tool (TaskCreate/TaskList) "does not exist in this build." As of Claude Code 2.1.269 (2026-09-11) it exists, gated behind an environment variable that is currently OFF by default on the models you run. The tool was never absent — it was off. Recommendation: keep it off (the cross-lane database task board is the real mechanism and nothing else reads a per-session task list), correct the 3 files so they stop asserting something false, and archive the premise while keeping any surviving instruction. See the strike list below — these 3 are flagged separately, not lumped into the pre-checked 64.
