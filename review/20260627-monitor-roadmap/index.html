Research — Council Pressure Test

What the audit found

Ran a 5-angle Council pressure test on the current dashboard (v2.5). Each angle scores 0–10 and names the single highest-leverage fix. This drives the Phase 1 roadmap.

WOW Factor 6/10

Visually strong (NASA grid, network map, glow tiles). Loses points because it shows machine states not business outcomes. "6 crews idle" means nothing to a prospect.

Fix: persistent outcomes counter in header — "14,678 LLM calls, $150 spent, 0 humans required"
Commercial 5/10

No call to action. No Calendly link. No translation from ops state to dollars saved. Prospects see lanes and tasks — they don't know what those mean for them.

Fix: ?share=1 mobile view + Calendly CTA (shipped v2.6). Outcomes strip shows ROI proof.
Trust Signals 5/10

No LIVE vs DEMO badge. A prospect doesn't know if this is real data or a staged demo. The throughput timeline can look flat on thin real data — reads as "nothing happening".

Fix: LIVE/DEMO badge + "last updated Xs ago" per panel. Shows it's actually running.
Resilience (Premortem) 4/10

WS disconnect = blank dashboard. If this drops during a demo, the whole UI goes empty. No fallback, no stale tolerance, no "reconnecting" badge.

Fix: cache last-known-good snapshot 5 min + amber "● reconnecting" badge on disconnect.
Mobile 2/10

4-col grid does NOT collapse on mobile. The ops view is completely broken on a phone. Can't show this externally until fixed.

Fix: ?share=1 view is mobile-safe (shipped v2.6). Full mobile responsive = Phase 1 stretch.

Design Brief — Locked 2026-06-27

Three pillars every feature must serve

Every build decision routes through this. If a feature doesn't serve at least one pillar, it doesn't ship.

1

Usability for You

Open it every morning, know fleet state in under 5 seconds. No hunting. No guessing. Data is real, not decorative.

2

WOW for Prospects

"Who built that?" on first glance. Cool visuals, meaningful outcome data, proves AI runs the business autonomously without your manual intervention.

3

Avant-Garde + Scalable

HITL intercept, self-healing agents, per-lane autonomy settings. Grows with more agents, more lanes, more clients. Not a dashboard — a living ops intelligence system.

Inspiration pulled from: NASA Mission Control (always-on status panels, anomaly alerts), Sentry (real-time event stream, "something is wrong" immediacy), Grafana (every tile earns its place), OpenClaw Nerve + TenacitOS (agentic ops aesthetic, network feel). What we are beating: Langflow / Dify — they show plumbing. We show outcomes.

What's Next

Build roadmap — Phases 1 to 5

1

Pre-Demo Polish

4 remaining items before showing this externally with confidence

Up Next
○
Outcomes strip in header — "X tasks done this week / $Y AI spend / 0 humans required". Turns machine state into ROI proof. Council said this alone moves WOW from 6→8.
○
WS resilience — cache last-known-good 5 min on disconnect. Show amber "● reconnecting" badge. Board never goes blank mid-demo.
○
LIVE/DEMO badge + "last updated Xs ago" — small badge per panel confirms real data, not a mockup. Kills the trust gap.
○
Fix browser title + insider language — "Pick yours ->" and internal codenames visible to prospects. Swap for plain English before demo.
Why this first

The ?share=1 link is ready to send but the full ops view still shows to prospects who get curious. Commercial score is 5/10. These 4 items are the minimum to stop showing a broken demo.

2

KPI Header Row (v2.7)

Slim data banner above the 3-col grid — orc-postgres only, no external failures

Next
○
SYS queue depth — COUNT work_items WHERE lane='systems' AND status != 'done'. Your backlog in one number.
○
Lead count from Supabase — lazy load, 3s timeout, shows 0 on fail. Never blocks the board.
○
Content drafts from Notion — count of Status=Draft items in the Content Board. Lazy load, 0 on fail.
Why

The 5-second morning scan currently tells you agent state. It should also tell you: how many leads exist, how many content pieces are queued, how many SYS items are open. Three numbers, top of screen, no clicking.

3

HITL + Self-Healing (v3)

Approve or reject agent actions before they fire. The "living ops" pillar.

Planned
○
New DB tables: hitl_approval_queue + agent_traces + workflow_runs in orc-postgres. Full schema in v3-enterprise-cockpit-spec.md.
○
WS events: HITL_REQUIRED / HITL_RESOLVED / TRACE pushed over /ws. Board lights up amber when an agent needs a decision from you.
○
Intercept card in center panel — amber card shows: what the agent wants to do, what tool it would call, what data it would write. Two buttons: Approve / Reject.
○
AutonomySettingsPanel — per-lane confidence slider + restricted tools list. You decide how much each lane can do without you.
○
Self-healing AgentToolExecutor — max 3 retries, exponential backoff, LLM self-correction on fail before escalating to HITL.
Why

This is what separates "AI dashboard" from "AI Operating System". Langflow shows plumbing. This lets you intercept, approve, or redirect agent decisions in real time. That's the demo moment that makes prospects ask "how do I get this for my business?"

4

Tabbed Departments

Research / Marketing / Sales / CEO / System — each tab owns its data source

After Phase 3
○
Research tab: absorb_queue pipeline health, PROCEED feed, source health, 30-day absorb rate chart.
○
Marketing tab: Notion Content Board calendar, draft/scheduled/published counts, queue velocity.
○
Sales tab: Supabase leads funnel — Discovered > Enriched > Contacted > Qualified. Deal flow in one view.
○
CEO tab: Aggregate KPIs across all sources + roadmap_logs progress bar toward 12-week Lighthouse target.
Why after Phase 3

Tabs have multiple external data sources (Notion, Supabase). Each can fail independently. Needed HITL + self-healing first so failures don't cascade into a broken demo. Building reliability before adding complexity.

5

Agentic BI

Your internal ops intelligence + CW client-facing read-only view as a product

Planned
○
Internal BI: cost trends, lane velocity, absorb ROI, content pipeline value. How much are agents actually saving you?
○
CW client BI: each CW client gets a read-only view of the work being done for them — tasks completed this week, time saved, AI spend on their account.
○
SYS item filed (2026-06-27) to scope this properly before any build starts.
Why

This turns the dashboard into a client retention tool. A CW client who can see their own BI view — "we completed 47 tasks this week, saved an estimated 23 hours" — is a client who renews. Requested by Boubacar directly 2026-06-27.

Decision Log

Why we made the calls we made

Serve boubacarbarry.com/monitor from Hostinger, not VPS
The VPS subdomain (agentshq.boubacarbarry.com) requires a Traefik config for the /monitor path. boubacarbarry.com is simpler to share publicly. Static frontend build deployed to Hostinger; WS/API calls cross-origin to VPS via VITE_WS_URL + VITE_API_URL.
Keep. Both URLs work. boubacarbarry.com/monitor is the public-facing share URL. VPS URL stays as internal backup.
Kill the 6-tab plan (CEO/Research/Marketing/Sales/System)
Tabs have too many external failure points (Notion, Supabase, VPS metrics) that can each independently break. Building reliability (WS resilience, self-healing) before adding complexity.
Changed. KPI header strip first (orc-postgres only). Tabs return in Phase 4 after Phase 3 HITL proves self-healing works.
dashboard-backend is IMAGE-BUILT, not volume-mounted
The multi-stage Dockerfile builds the React frontend INTO the image. Any code change requires docker compose build, not restart. This was the source of a silent stale-code bug (v2.5 session — restarted without rebuilding, served old code for hours).
Keep. This is correct architecture (frontend baked into image = one artifact). Mitigation: always rebuild + up -d, never restart alone.
?share=1 as URL param, not a separate domain
Keeps a single build and single deploy. The share view detects the param at runtime. No additional DNS, no separate build pipeline. Prospect gets /monitor?share=1 link; Boubacar uses /monitor directly.
Keep. Clean separation of concerns with zero infra cost.
