Where the SIL research doc does and doesn't apply

The SIL doc is 36 sections about building a commercial product for service organizations (industrial field-service knowledge capture). It's not a dashboard spec - "dashboard" appears once, in a Phase-2 bullet.

Where it genuinely does apply: as design doctrine. Its architecture principles map cleanly onto the truthfulness problem the Atlas board already has - real event sources instead of caches, provenance on every number, no fake "it fired so it must have worked." All of that is echoed in the done-checklist below.

What it does not mean: do not modernize Atlas toward the SIL stack (graph databases, ontologies, multi-model routing). The SIL doc's own rule (§32) bans building the platform before the narrow workflow works - and Atlas is the narrow workflow that already works. Its boring stack (static HTML + vanilla JS + PIN + FastAPI JSON) is a feature: zero build step, deploys with a docker compose restart, live for months.

The recommendation: Option A

Option A - Extend Atlas, demote the monitor to demo-only

Fold tonight's paused branch in, add the agent-roster tile from the existing manifest, regroup tiles by question, port anything unique from the monitor, formally redesignate dashboard/frontend as the client demo prop.

Effort: S-M (tonight's branch is ~70% of the tile work)  |  Risk: Low, additive/read-only/auth-gated  |  Reversible: Yes

Option B - Resurrect the React build as the one board

Finish dashboard/frontend, flip the manifest flag, port all 16 tiles into React, retire atlas.html.

Effort: L  |  Risk: High - image-built, publicly routed, no PIN, data layer unfinished  |  Reversible: Poorly

Option C - Build fresh

Effort: XL  |  Risk: Highest - this is the exact move your instruction was issued to prevent. Recommend against without further argument.

Why Option A

  1. Atlas already wins on every hard criterion: live, PIN-authed, 15 real endpoints, 13 routed sub-pages, test coverage, zero build step. The monitor is publicly routed, image-built, fixture-backed, and unused.
  2. The cheapest path to "what Atlas was supposed to be" is one tile, not one rewrite. agent_manifest.yaml already has the fields the June spec wanted. Nothing reads it today.
  3. The dual-audience problem is the real bug - and Option A is the only option that actually fixes it. B and C both inherit the "one surface, two masters" trap that stalled the June build.
  4. Tonight's paused branch is already most of the work and stopped in exactly the right place, before live verification.
  5. The SIL doc's own rule says so: don't build the platform before the narrow workflow works. Atlas is the narrow workflow that works.
What you're actually deciding is not "which framework" - it's whether you want one surface serving both you and prospects, or two surfaces with clean separation. The first attempt at "one surface" already failed, on record, for a nameable reason.

Machine-verifiable "done" checklist

Every line below is checkable by a script or a screenshot - no judgment calls. A future build task on this is not done until every box passes.

15-item checklist

Data truth

  • Every polled endpoint returns HTTP 200 with non-empty JSON. Zero 404s, zero 500s.
  • Every tile's JSON includes a source identifier and timestamp, or an explicit {"available": false, "reason": "..."}.
  • No tile renders a number from a cache, fixture, or hardcoded constant - grep -r "fixture" on the ops path returns nothing.
  • Every tile reading a laptop-written or possibly-stale source states that on screen, in words.

Consolidation

  • agent_manifest.yaml is read by at least one live Atlas endpoint; roster tile renders with function_group grouping.
  • COMMAND_CENTER_USE_LIVE_MANIFEST is set in docker-compose.yml, or the fixture path is deleted - no half-wired state.
  • No ops question is answerable only at /monitor. Each of the 6 tabs is either ported to Atlas or explicitly declared demo-only in writing.
  • Every nginx /atlas/* route resolves to a page that fetches live data or is explicitly labeled a static snapshot.

Verification

  • Playwright screenshot of /atlas at desktop width and 375px, after full load, actually looked at (standing visual-verification rule).
  • Hamburger nav present below the mobile breakpoint (standing mobile rule).
  • PIN auth confirmed still required - an unauthenticated curl to each new endpoint returns 401/403, never data.
  • test_atlas_dashboard.py passes, with new tests covering each new function's missing-data path.

Non-regression

  • No new endpoint mutates anything - every added route is a GET.
  • Board first paint under 3 seconds on a cold session, measured not estimated.
  • docs/LIVE_STATE.md carries a row for the canonical Atlas URL - it does not today, and that's its own small defect worth fixing in the same pass.

What NOT to build

7 hard nos for this pass
  • No new framework, no React rewrite of Atlas, no build step.
  • No graph database for the ops board.
  • No third dashboard, under any name, for any reason.
  • No tile that answers a question you haven't actually asked.
  • No auto-refresh faster than 30 seconds.
  • No write actions added in the same pass as consolidation - read-only first.
  • No retirement of command-center.html until the nginx route is re-verified and its inbound links are checked.
