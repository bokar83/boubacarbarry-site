Where agentsHQ sits on the maturity ladder, and the two moves that matter

A full read of Google's agent-maturity whitepaper, cross-checked against agentsHQ's actual memory system and agent-to-agent messaging code — not the docs about them.

2026-08-30 100% of the source document read (1,197 lines) Focus: memory & A2A

TL;DR

The paper's own ladder only goes to Level 4, and its Conclusion calls Level 3 “the frontier of automation” today — Level 4 is presented as aspirational. agentsHQ is a genuine Level 3 system already, with one authentic Level 4 piece most published systems don't have: the human-correction-becomes-a-permanent-rule learning loop your memory system already runs.

The two areas asked about are exactly the two weakest Level 3 pillars. Memory pushes everything into context eagerly and rations it against a byte cap; the paper says long-term memory should be something an agent can actively query, like a RAG system over a vector database — that retrieval layer doesn't exist over your memory files today. Agent-to-agent messaging exists and works, but it's pull-only, one-shot (capped at one reply per lane by design), and has no capability registry — a dispatcher has to already know who owns what.

Three concrete, incremental fixes close most of the gap: add semantic search over the memory corpus (pgvector, already-idle infrastructure exists for it), add a lightweight lane/capability registry, and link messages to tasks so a delegation can actually be tracked and replied to more than once. No platform rewrite, no A2A protocol adoption — those solve a cross-organization problem you don't have.

01

The paper's maturity framework

The paper defines Level 0 through Level 4 — there is no Level 5 in this document. lines 43-51, 289-385

L0Core Reasoning System — the model alone, no tools, no memory
L1Connected Problem-Solver — tool use / RAG, reaches outside training data
L2Strategic Problem-Solver — context engineering, actively curates context per step
L3Collaborative Multi-Agent System — a coordinator delegates to specialist agentsagentsHQ is here
L4Self-Evolving System — identifies its own capability gaps and creates new tools or agents on the flypaper calls this aspirational

The paper's own Conclusion calls L3 “currently constrained by the reasoning limitations of today's LMs” and names it the practical frontier. lines 365, 915

Honest fit caveat: the paper's L3/L4 assume a cloud-native platform — Gemini Enterprise Agent Platform, ADK, Agent Gateway, Agent Registry, SPIFFE identity. agentsHQ is Claude Code CLI + Postgres + markdown skills. Several L3/L4 markers are platform features that don't transfer. The ones that do — memory retrieval, agent discovery, task-oriented messaging, agent identity, the learning loop — are what this review scores.

02

What the paper says about memory

Memory is an orchestration-layer concern in this paper, kept deliberately brief — it defers to a dedicated agent-memory whitepaper elsewhere in the series. line 485

  • An agent is framed as “a system dedicated to the art of context window curation” — a loop of assembling context, prompting, observing, and re-assembling for the next step. line 199
  • Short-term memory = the active scratchpad, the running action/observation history of the current loop — implemented as state, artifacts, sessions, or threads. line 487
  • Long-term memory, the load-bearing line: “architecturally, this is almost always implemented as another specialized tool — a RAG system connected to a vector database or search engine. The orchestrator gives the agent the ability to pre-fetch and to actively query its own history.” line 489
  • Retrieval substrate named: vector databases or knowledge graphs, plus NL2SQL for structured data. line 433
  • Memory is the fuel for learning: agents learn from session logs, traces, and memory capturing successes, failures, and decision trajectories — crucially including human-in-the-loop corrections as authoritative signal. line 777

The paper says nothing about memory conflict resolution, staleness/TTL, or byte budgeting — those are agentsHQ's own problems to solve, not addressed by the source.

03

What the paper says about A2A
  • “Agents are not tools.” Connecting an agent to data/APIs (MCP) is a different problem from connecting an agent to another agent — A2A is “typically for additional problem solving,” not transactional requests. lines 585, 613
  • The core challenge is twofold: discovery (how does my agent find others and know what they can do?) and communication (how do we ensure they speak the same language?). Without a standard you get “a tangled web of brittle, custom API integrations.”
  • Agent Card — the discovery primitive: a JSON “digital business card” advertising capabilities, network endpoint, and required credentials. line 613
  • Task-oriented, asynchronous architecture — the communication primitive: a client agent sends a task request to a server agent, which provides streaming updates over a long-running connection, rather than simple request-response. Named explicitly as what enables Level 3 collaboration. line 615
  • Named multi-agent patterns: Coordinator (manager routes and aggregates), Sequential (assembly line), Iterative Refinement (generator + critic loop), HITL (deliberate human-approval pause). lines 491-511
  • Agent Identity as a third class of principal — distinct from user (OAuth) and service account (IAM), a cryptographically verifiable identity so permissions contain the blast radius. lines 649-679
  • A mandatory governance control plane (Agent Gateway) that all traffic passes through, plus a central Agent Registry indexing every agent/tool/skill with security review before publication. lines 731-753
04

agentsHQ's memory system, verified

Storage: 1,981 flat markdown files in memory/, each with frontmatter (tier: always-load | archive, index_line:) read by scripts/build_memory_index.py.

Loading is push, not pull. memory/MEMORY.md is a generated index held under a 24,400-byte cap by construction — overflow rows route to memory/MEMORY_LOADER_OVERFLOW.md, injected by a SessionStart hook. Everything a session gets is eagerly pushed at session start, none of it queried on demand.

Hand zone: four sections are DB-backed in Postgres (memory_handzone table), regenerated into the file. One stale doc found in passing: docs/governance/memory-handzone-db-backed-sys264.md still says “NOT yet cut over” while CLAUDE.md says cutover happened 2026-07-13.

Retrieval — the weak point, verified directly: skills/second-brain-query/ask.sh is tsvector lexical search only — its own header says so. A prior live audit (docs/governance/second-brain-retrieval-verdict-2026-08-20.md) found two natural-language queries returned zero results, the one hit that did return scored 0.0164 relevance on a superseded file, and the corpus was 4 days stale. Its own verdict: “it works, and it is pointed at the wrong shelf.”

The only embedding-based recall in the repo (skills/atlas-memory, MiniLM + sqlite-vec) indexes session transcripts, not memory files — and its MCP connection was down this session. Conclusion, independently verified: there is no semantic/vector search over the memory corpus today.

05

agentsHQ's A2A system, verified

skills/agent_comms.py (532 lines, read in full), backed by a Postgres agent_messages table.

  • Pull-only, by the module's own docstring: “a message arrives when the recipient polls fetch_inbox(). No daemon, no push, no pub/sub, no threading.”
  • Near-real-time is a poll loop, not push: an opt-in watcher SSHes to the VPS every 3 seconds to check a sentinel file. No webhook, no long-lived connection. One real push exists — urgent=True fires a Telegram alert — but that's agent-to-human, not agent-to-agent.
  • Multi-turn dialogue is structurally blocked: reply_message() uses a dedup key of exactly one reply per lane per original message, by design. No thread_id column exists. No negotiation, no back-and-forth is possible today.
  • No agent identity: from_lane is unauthenticated free text. Any caller can send as any lane.
  • No discovery / no Agent Card: lane names are hardcoded strings scattered across docstrings and docs, not a queryable capability manifest.
  • A real task-lifecycle state machine exists — in a separate, unjoined system. skills/coordination has claim/complete/lease-renew/fail with TTL leases. None of it links to agent_messages — a delegation message carries no task id and no trackable status.
  • What is genuinely strong: the Coordinator, Sequential, Iterative-Refinement (critic), and HITL patterns the paper names are all real and working — Agent-tool dispatch, the worktree→Gate deploy chain, `karpathy`/`council`/`code-review` as critic agents, and the Tier-C damage-list human-approval gate.

Where agentsHQ actually sits: a solid, in-places-excellent Level 3, with one authentic Level 4 component most published systems lack — the correction-to-durable-rule learning loop. The two areas asked about are, precisely, the two weakest Level 3 pillars.

The single most important structural finding: the paper says long-term memory should be something an agent can actively query. agentsHQ inverted this — it pushes memory eagerly into every context window and rations it against a byte cap. That inversion is the direct cause of the loader-cap fights, the CLAUDE.md mirror sections, and the recurring “rule didn't load” incidents. It is an architecture problem, not a tuning problem — it gets more expensive as memory grows, since every byte is paid on every one of ~401 weekly dispatches.

07

Prioritized recommendations

Ranked by movement toward the paper's L3/L4 bar and feasibility on the actual stack. No rewrites — every item extends something that already exists.

P0
Semantic retrieval over memory: flip push to pull

Add pgvector to orc-postgres and embed the existing memory corpus; blend with the current tsvector rank rather than replacing it. Extend second-brain-query/ask.sh with a --semantic path.

Three things must ship with it or it repeats the 2026-08-20 failure: fix the corpus itself (add LIVE_STATE.md, governance docs, handoffs — retrieval that can't see your sources of truth keeps returning superseded files), make staleness an alarm not a footnote, and down-rank archived/superseded files as a ranking signal.

Free adjacent win: the atlas-memory MCP (working semantic recall over session transcripts) was disconnected this session — reconnect it, it's already built and paid for.

P1
Agent Card registry — a lanes table

One migration: lane, description, capabilities (JSONB), owner machine, active claims, last-seen. Expose via agent_comms lanes [--capability x]. Populate last-seen automatically on every inbox fetch — free liveness tracking, zero discipline required.

Smallest change, largest compounding effect: today a dispatcher must already know that a given lane exists and owns a given area — that's why rules like “hands off UpWork” had to become hard-coded prose instead of a lookup.

P2
Join messages to tasks; add real threads

Add a task_uid column linking to the existing coordination state machine (already has claim/renew/fail/complete with lease heartbeats — just not wired to the message bus). Add a thread_id and relax the reply dedup from per-message to per-turn, so multi-turn dialogue is possible by design instead of blocked by design.

Not recommended alongside this: a push/websocket layer. The 3-second poll is adequate for lanes operating on human timescales; a daemon adds an always-on failure mode for latency nobody is waiting on.

P3
Minimal agent identity

Record actual sender (hostname, session id, a per-lane token) alongside every claim, and flag a mismatch rather than trusting free-text from_lane. Do the cheap version; skip SPIFFE-grade cryptographic identity — not warranted at this scale, but the urgent Telegram-escalation path in particular deserves this before something is forged into it.

P4
Golden eval set + LM-as-judge regression gate

Hundreds of feedback_*.md incident files already exist as an unlabeled golden dataset. Convert ~30 high-frequency ones into scenario/expected-behavior pairs and run a judge model on a schedule — turns “did the agent follow the rule” from something caught by a human noticing into something the system measures.

P5
Formalize the Learning Agent loop already running informally

The correction-to-rule loop works but depends on someone remembering to run it at checkpoint. Make it an explicit dispatch after any correction: draft the memory file, check it against existing rules for contradiction/supersession (no such check exists today), then file it.

×
Explicitly not recommended

Agent Gym / simulation: presumes offline platform + synthetic-data infrastructure that costs more than the lanes it optimizes. AP2/x402 payments: nothing in this system transacts autonomously, and money deliberately stays on the human side. Full A2A protocol / Agent Gateway adoption: built for cross-organization interoperability between separately-built agents — your lanes share one repo, one Postgres, one operator. The three Postgres changes above take the useful ideas (Agent Card, task-oriented messaging, identity) without the platform rewrite.

Sequencing: P0 and P1 are independent and can run in parallel. P2 depends on P1. P3 depends on P1. P4 and P5 are independent of everything and can start any time.
