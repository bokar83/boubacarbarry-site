I followed the actual /newcompany skill procedure line by line: directory scaffold, knowledge base with its own embedded git repo, manifest registry entry, a real business-discovery write-up of how Catalyst Works actually runs, and two workers (growth-ops, delivery-ops) modeled on my real cold-outreach and delivery workflow, not the demo defaults.

The install

Repo: indigoai-us/hq-core. Installed via npx create-hq with --minimal --skip-sync --skip-packages --skip-cli, deliberately closer to what a first-time Windows evaluator would actually get than a fully dependency-loaded install. Pinned at hqVersion 15.0.116, create-hq CLI v10.12.10, and never re-run or hq updated for the rest of the weekend, so this teardown describes one fixed, reproducible state rather than a moving target.

Environment: Git Bash on Windows 11, Node v24.18.1 / npm 12.0.2, GitHub CLI present, qmd and the global hq CLI intentionally absent (minimal mode).

Already-known friction going in: the guided /setup wizard assumes macOS tooling — Homebrew, qmd installed via brew+sqlite, gh installed the Mac way — while the base create-hq scaffold itself ran cleanly under Git Bash with no changes needed. The scaffold and the setup wizard are two different pieces of software with two different levels of Windows readiness.

Scaffolding Catalyst Works — the real company, not a fictional one

Jacob's own bar is familiarity with the product, and a fabricated client would be the one thing most likely to read as staged to the person who built it. So I scaffolded my own practice instead: catalyst-works, prefix cat, computed the way the skill's procedure says to (strip hyphens, lowercase, first three characters, checked against existing prefixes in manifest.yaml, which was empty).

I followed HQ Core's own .claude/skills/newcompany/SKILL.md procedure directly — the same Markdown that drives the /newcompany slash command inside a live Claude Code session — rather than opening a second nested interactive session, since I was already operating as an agent with shell and file access. That is an honest description of how this was done, not a slash-command transcript; I want that distinction on the record rather than implied.

What got built, following Phase 0-3 of the skill exactly

  • Phase 0 — scaffold: companies/catalyst-works/ with settings/, data/, workspace/, board.json seeded with the empty objectives/initiatives/projects shape the skill specifies, and company.yaml with cloud: false (the documented local-only default).
  • Knowledge base: a real directory (not a symlink — verified per the skill's own check) with its own embedded git repo, per the skill's explicit warning that a symlinked knowledge dir uploads as a ~50-byte marker and breaks team sync.
  • Business discovery (Phase 1), with real facts, not filler: company-info.md and business-model.json describing how Catalyst Works actually operates — the fractional-operator pitch, the reply-first cold-outreach model, the parachute-test rule that the client list can never depend on warm network, ROI-anchored pricing over hourly billing, and async-first delivery.
  • Two workers (Phase 3), modeled on the real workflow: growth-ops (cold discovery, sector-vs-size template selection, no Calendly link in the first touch, no weekend sends) and delivery-ops (engagement scoping, ROI-anchored pricing, async-first delivery, stay-on partnership framing). Both carry approval_required: true — nothing in either worker's spec authorizes an unreviewed send or an unreviewed price.
  • Registry: a real manifest.yaml entry with the computed prefix and knowledge path.

Skipped, deliberately, per the PRD's own tech boundary: Phase 2.5 (brand packs), Phase 4-8 (cloud provisioning, team ACLs, integrations, invites, cloud agents) — those require the hosted vault-service backend and a live team, out of scope for a solo weekend evaluation with no VPS component.

Real terminal output

These are the actual commands and actual output from this weekend's session, not reconstructed after the fact. Five genuine findings came directly out of running this, not out of reading the README.

1. A doc reference that does not exist in the scaffold

The /newcompany procedure says to copy companies/_template/.obsidian into every new company. It is not there:

$ ls companies/_template/.obsidian
ls: cannot access 'companies/_template/.obsidian': No such file or directory

Not fatal — the step is written defensively ([ -e ... ] &&) so it fails soft. But the documented Obsidian-vault-config step is currently a no-op on a fresh scaffold, and nothing in the skill's own output says so.

2. The skill tells you to edit a file the tool declares locked

Phase 0.7 says: "If CLAUDE.md's ## Companies line doesn't include the new slug, update it." core/core.yaml, HQ Core's own lock manifest, declares:

rules:
  locked:
    - .agents/
    - .claude/
    - .codex/
    ...

There is no top-level CLAUDE.md at all — only .claude/CLAUDE.md, which is inside the tool's own locked path. The skill's documented instruction targets a directory the tool declares immutable. I did not edit it, and I'm noting the contradiction rather than quietly resolving it either way.

3. The minimal install has no working CLI, so most of the pipeline is inert

$ hq reindex
bash: hq: command not found

$ npx --yes @indigoai-us/hq-cli reindex
npm error could not determine executable to run

This is the direct, load-bearing consequence of the --skip-cli minimal install: the workers registry auto-generation, hq groups/hq secrets/hq files share/hq members invite — the entire Phase 4-8 integration/ACL/invite layer the skill describes — simply cannot run without the CLI, and the documented fallback (npx @indigoai-us/hq-cli) doesn't resolve to an executable either. A first-time Windows evaluator staying in minimal mode, as the wizard's own macOS-tooling friction would push them to do, hits a wall well before the "operational" half of what /newcompany promises.

4. qmd absent (expected, and confirms the doc's own dependency posture)

$ qmd collection add companies/catalyst-works/knowledge --name catalyst-works --mask "**/*.md"
bash: qmd: command not found

Documented and expected in minimal mode — knowledge search/reindex depends on a tool that has to be installed separately via Homebrew, which is the same macOS-first assumption already flagged for /setup.

5. A small internal contradiction in the manifest schema example

The skill says every manifest field must be populated, "no nulls" — then shows github_org: {org or omit} as the literal field template for a company with no GitHub org. Those two instructions conflict for the one field a solo practice like mine actually needs to omit. I resolved it by leaving the key out entirely (matching the "no nulls" spirit) rather than writing a literal placeholder string, and confirmed the resulting YAML still parses.

Committing the scaffold surfaced one more real thing

$ git add -A -- companies/manifest.yaml companies/catalyst-works
warning: adding embedded git repository: companies/catalyst-works/knowledge
hint: You've added another git repository inside your current repository.
...

The embedded-git-repo pattern for the knowledge directory is deliberate per the skill's own instructions (needed so cloud sync uploads real files, not a symlink marker) — but it throws Git's standard submodule warning on every single commit that touches it, with no suppression built into the scaffold. Cosmetic, not a defect, but it is the kind of "does this look broken" moment a first-time user would stop and second-guess.

The honest teardown

What's genuinely good

The scaffold-first design is the right call: Phase 0 always leaves you with a working company directory in seconds, and everything past that — business discovery, brand packs, workers, team ACLs, invites, cloud agents — is explicitly fail-soft and skippable, rolling into a finish-later checklist instead of blocking. That's a real architectural decision, not a marketing line; I could see it directly in how the skill is written. The company/knowledge separation (a real git repo per company, never a symlink) is a deliberate, correct choice for a product whose whole thesis is that context should sync across a team — a symlinked "vault marker" would quietly break that thesis for anyone who tripped into it.

What surprised me

How much of the "team AI operating system" pitch depends on the hosted vault-service backend and the hq CLI specifically, not on the local scaffold. The local-only path (what I ran) gives you real structure — knowledge, workers, policies, a board — but the actual compounding-memory mechanism the README leads with (shared context synced across a team, connected tools, ACL-scoped access) is gated entirely behind provisioning a cloud vault. That's a reasonable product boundary, but it means "installed HQ Core" and "have the thing HQ Core is actually selling" are two different states, and the gap between them is not obvious from the README.

What's rough

Windows readiness is uneven across the product's own surfaces: the base scaffold is clean, the guided /setup wizard assumes Homebrew, and the documented CLI fallback path (npx @indigoai-us/hq-cli) doesn't actually resolve on a fresh machine. For a company whose install command is npx create-hq — the single lowest-friction install pattern in the Node ecosystem — the CLI it hands you off to next is the highest-friction thing in this teardown.

What's genuinely missing (for a domain I know)

Nothing in the scaffold, the policies, or the skill library speaks to large-org HR/ops rollout mechanics — stakeholder alignment, change-management sequencing, executive sponsorship. That's not a knock; HQ Core's own customer base is clearly engineering/product teams shipping code with Claude/Cursor/Codex, and it's honest about that. It is real white space relative to what I do, which is the whole reason the next section exists.

Scope sketch: a large-org HR/ops rollout HYPOTHETICAL
HYPOTHETICAL — not a real engagement, not a real client, not a real result

This is a scope sketch, built to answer one question directly: given what Jacob himself named as the number one success factor for any implementation — "the highest possible level executive alignment... the human element of it is more important than the tech at this point" — how would I actually scope a large-org HR/ops rollout of HQ Core? No client is named or implied. No numbers below are results; they're a sequencing sketch.

Phase 1 — executive alignment before a single skill is written

Before any scaffold work: identify who actually owns the outcome (usually CHRO/COO plus the functional VPs whose teams will feel the change), get them in a room together, and get explicit agreement on what "working" looks like in their terms, not HQ Core's terms. This is the phase most implementation partners skip because it isn't billable-looking work — it's exactly the phase Jacob flagged as the actual determinant of success.

Phase 2 — one function, not the whole org

Same Phase-1-through-3 scaffold shown above (company, knowledge, business discovery, one or two workers) but scoped to a single function with a visible, checkable win — the function whose executive showed up in Phase 1 with real skin in the game, not the function that's easiest technically.

Phase 3 — a checkpoint that can say no

A named go/no-go review with the same executives from Phase 1, using the same "working" definition they set, before touching a second function. This is the review-and-pivot point HR/ops rollouts routinely skip in favor of a fixed multi-phase plan that nobody re-checks against reality.

Phase 4 — expand only on a proven win

Additional functions get the same treatment, in the order their executives are ready to sponsor — not in the order that is easiest to build.
