Four fifths of the bill is a monitor asking the system whether it is awake. It burns 4.5 million input tokens a month to do it, because it does not just ping. It runs a full reasoning agent and asks it a real question, on the premium model, roughly once an hour, forever.

This was caught before. In June the same check was found eating about $140 a month and the fix cut how often it runs. The other half of that fix, written down at the time as "probe with a cheap model", was never done. Three months later it is still the single largest line item.

I did not change it, deliberately. Its model is set by the live chat agent it calls, so making it cheaper would stop it testing the real thing, which is the entire point of a health check. And its schedule lives on the server outside version control, which puts it in shared infrastructure. The right fix is the one nobody has asked yet: why is a liveness check running a functional test on the same timer? A cheap ping every few minutes and a real functional test once a day would cost a fraction and tell you more. That needs a decision and an owner, not a drive-by edit.

After a model was retired out from under the system and broke the same content flow three times in a row, a daily checker was written to catch the next one within a day. It was designed, reviewed, and shipped. It has zero schedulers and zero callers. It has never executed.

And the routing code carried two comments stating, as fact, "the daily check catches the next death within 24 hours." That sentence was false the entire time it sat there. Anyone reading that file, human or agent, was told the room was monitored. I corrected both comments to say plainly that nothing is watching.

Three separate mechanisms built to keep this honest. None of them running. The common thread is that every one of them was designed to need a person to remember to start it.

I have written the one-line installer that makes the daily check real. I have deliberately not run it, because adding a scheduled job to the server is shared infrastructure and that is your call. It is a yes or no, and it takes ten seconds.

Two decisions for you

1. Install the daily model-death check?

The checker exists, is written, and has never run. Installing it means one scheduled job that makes one web request a day and sends you a message only if something it depends on has been retired. It never changes any setting on its own. It touches shared infrastructure, which is why it is your call and not mine.

  • Yes is my recommendation. This is the cheapest insurance available against a repeat of the failure that broke the same flow three times.
  • No is defensible too. Nothing is dead right now, I verified all 20 by hand today, and you would be accepting that the next retirement is found by something breaking.

2. Should the next review look at a different bill entirely?

This whole audit covered a system that costs $18.45 a month. That is real but it is small. The reasoning you actually rely on all day, the sessions that plan and build and argue with you, runs on your subscription, which is a different and far larger bill. I was scoped out of touching that deliberately, and it is the right scope for a code change. But if the question behind your question was "am I paying for the right brains", the answer lives on that other bill, and I would point the next review there.

Not a decision, but it needs an owner: the health check eating 83% of this budget. It should be split into a cheap frequent ping and a real functional test that runs once a day. It has now been flagged twice, three months apart, and gone unfixed both times. It needs a date on it or it will be flagged a third time in December.
